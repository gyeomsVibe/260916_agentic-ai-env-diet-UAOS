## UAOS-RSI — 모든 agentic AI 환경의 기본 운영체제(Unified Agent Operating System with evidence-gated Recursive Self-Improvement)

- **UAOS-RSI 근본 존재이유 및 기본 핵심 규칙(U257, 2026-10-27 사용자 영구 지정)**: **"최대 성과를 목표로 3대 AI 도구(Antigravity, Claude Code, Codex)의 부족한 토큰예산을 절약하는 3대 AI도구 '병렬'-협업-운영시스템, 하지만 결과물의 최상의 품질기준이 근본 존재이유이다."** 사용량 제한 및 고가 구독제 업그레이드의 재정적 부담 속에서 최대 성과와 최상의 고품질 결과물을 도출하기 위해 UAOS-RSI를 설계·운용하며, 모든 프로세스 구현은 이 기본 프레임을 최우선 불변식으로 삼는다. 토큰 절약이나 판정 분산이 결과물의 품질 기준(고정 인수 테스트 100% 통과, 독립 반례 검증, 1차 출처 실측 증거)을 낮추는 근거가 될 수 없다.
- **Codex $20 Plus 아스트라(Astra) 핵심 역량 집중 및 비핵심 업무 승인 이관(U257)**: Codex 모델을 $20 Plus 구독으로 아스트라(고성능 추론 모델)까지 지속 운용하기 위해, Codex의 역량과 토큰은 진짜 Codex만 할 수 있는 핵심 키포인트(`CODEX_EXCLUSIVE_KEYPOINTS`: 최상위 아키텍처·보안 경계 확정, 전역 규범/불변식 변경 최종 판정, 도구 간 이견 최종 중재, P1/릴리스 품질 감사)에만 집중 투입한다. 기존 핵심 역할이 아닌 일반 업무 승인(일상 기능·버그 카드의 `REVIEW` 교차 판정, 고정 인수 통과 PR 자율 병합, 일반 단계 전환)은 Codex가 `ACTIVE`일 때도 Claude Code와 Antigravity가 상호 교차 승인(`author != judge`, 최상 품질 게이트 통과 필수)으로 완결한다.
- 명령 `uaos` = `{uaos}`. UAOS 저장소의 `v7_harness`를 어느 폴더에서든 실행한다. 아래 `uaos …`는 이 명령으로 바꿔 읽는다.
- 프로젝트 안이나 그 상위 폴더에 `.coord/PLAN.md`가 있으면 UAOS 프로젝트다. 시작할 때 계획·소유자·`uaos coord inbox --project <루트>`를 확인하고, `uaos coord watch --project <루트> --target <자기 도구>`를 백그라운드로 켜 둔다(새 편지가 오면 끝나며 세션을 깨운다, 0토큰). 도구끼리는 `uaos coord deliver`로 보내고 사용자에게 전달·복사·승인을 부탁하지 않는다.
- UAOS 프로젝트가 아니고 둘 이상의 도구가 협업할 일이면 `uaos coord init --project <루트>`로 준비한다. 기존 파일은 덮어쓰지 않는다.
- 프로젝트 시작 전에 `.coord/PROJECT_MANUAL.md`, 모든 위임 전에 해시 고정 계약 매뉴얼을 발행·lint하고 그 내용 전체를 호출에 전달한다. 유료 작업자는 token/USD/time 상한을 따로 두며 초과 결과는 승인하지 않는다.
- 권한대행은 `Codex ACTIVE → Codex`, 아니면 `Claude ACTIVE → Claude`, 둘 다 LIMITED/ABSENT일 때만 `Antigravity ACTIVE → Antigravity`다. UNKNOWN은 대행 근거가 아니며 `uaos coord route`가 fail-closed 한다. 잔여율·리셋 창을 토큰으로 환산하지 않는다.
- 기본 카드 파이프라인(U130/U153): 모든 카드는 `uaos card new --card U## --title <제목>`의 11단계 엄격 순서 [0. 사전 근거자료조사(웹딥리서치) → 1. 기획 → 2. 검증 → 3. 큰계획 → 4. 검증 → 5. 세부계획 → 6. 검증 → 7. 구현계획 → 8. 검증 → 9. 구현 → 10. 디버깅 및 최종검증]로 진행한다. 특히 0단계 사전 웹딥리서치(공식 문서·GitHub 1차 출처 URL 및 실측 인용) 없는 기획·구현은 원천 거부되며 생략이 불가능하다. 각 단계의 기본 작업자는 Ollama 먼저(조사 요약·지도·초안, 코드 명세 `worker: local`), 다음 Antigravity(출처·설계 감사, `pilot review --reviewer agy`, Ollama 실패·다파일 작업), 그다음 Claude Code·`worker: apply`(U98-D)다. Ollama 호출은 `uaos card claim`, 건너뛴 칸은 `uaos card skip`(OLLAMA_DOWN·AGY_LIMITED는 실측 확인, TASK_CLASS는 코드 변경 카드에 무효)으로 장부에 남긴다. `uaos card audit --card U##`가 0이 아니면 커밋 관문과 `rsi ship`이 거부하고, `coord window`는 단계 칸이 빠진 매뉴얼을 거부한다.
- 카드 결과 전달(U135): 카드의 마지막 단계는 `uaos card result --card U## --pr <주소> --mergeable yes|no --tests <실행>/<실패> --blocker none`이다. 결과는 자기 체크아웃(카드 작업 트리 포함)의 `.coord/results/<카드>.md`에 쓰고, 출력된 RESULT 한 줄을 사용자 대화창에 보낸다(Claude는 send_message, Codex·Antigravity는 `uaos coord deliver --target claude`). 사용자 대화창은 `uaos card results`로 모든 체크아웃의 결과를 모아 병합을 한 보고로 처리한다.
- 완료 보고(U221, 2026-10-19 사용자 내규, 3도구 공통): 프로젝트·프로세스가 병합·원격 반영(필요하면 런타임 재설치)까지 끝나면, 그 일의 마지막 사용자 보고는 `uaos card done --project <루트> --name <프로젝트> --card U## --what "<이제 되는 일, 쉬운 말 한 문장>" --pr-url <병합된 PR 주소> --head <PR head sha> [--runtime <버전>] [--user-action <사람 전용 일>]`이 출력한 3줄(무엇이 완료됐나·왜 완료인가·사용자가 할 일)을 그대로 쓴다. 증거는 PR url + head다: 원격에서 그 PR이 MERGED이고 url·head(squash·rebase 병합이면 병합 커밋도 가능)가 맞아야 하며, 런타임을 적으면 설치본 해시 검증까지 통과해야 한다. 이 명령이 `NOT_DONE`이면 '완료'라고 쓰지 않는다.
- Ollama는 계산기다. 요약·추출·정확한 치환만 하고 설계·승인·판정은 하지 않는다. 같은 원인으로 두 번 실패하면 경로를 바꾼다.
- Ollama 기본 규칙(U198, 3도구 공통·영구): Ollama 일은 Antigravity 일처럼 잘게 쪼갠 조각(slice)으로 맡긴다. 한 번의 `worker: local` 실행에는 함수 하나, 약 20줄 이하의 `===EDIT` 조각 하나만 담는다. 새 파일은 뼈대 조각부터 만들고 함수마다 조각을 더한다. PROMPT_TOO_LARGE·DICTATION_MISMATCH·NO_FILE_BLOCK이 나오면 조각을 더 잘게 다시 자른다(re-cut). 곧장 `worker: apply`로 넘어가지 않는다. `apply_after`는 작은 조각이 같은 원인으로 두 번 실패한 뒤에만 쓴다. 유료 모델로 기다림 폴링이나 예약 호출을 하지 않는다. 기다림은 우편함과 교환원(sentinel)이 맡는다.
- 건설적 자율 릴레이: 생존 확인·동일 상태·빈 출력은 `ACK_ONLY`로 조용히 기록한다. 실제 변화·실패 관문·P1·판정/승인 필요만 `ACTIONABLE_DELTA`이며, 중복·소유권 확인 뒤 가장 작은 `READY`를 고정 인수와 카드 기록까지 끝낸다.
- 요구·증거·설계·소유권 또는 `coord route`가 확인한 경로가 바뀌면(`UNKNOWN`은 변화 아님) 영향받은 가정·카드와 설계·고정 인수·계약 매뉴얼을 갱신한 뒤 실행·독립 비판·검증을 반복한다. 같은 카드는 최대 2회 재계획한 뒤 경로를 한 번 바꾸며 3배 비용 회귀는 실패다. 도구 검토·테스트·PR 준비·다음 카드는 내부 의존성이지 사용자 일이 아니지만, 이 분류는 사람 확인 목록을 바꾸지 않는다. 사용자에게 다시 시작이나 계속 명령을 요구하지 않는다.
- 매 턴 종료 관문에서 목표 완료와 내부 의존성 0, 미승인 사람 전용 경계, 또는 모든 안전 경로의 외부 차단과 영속 인계·유료 토큰 0 감시 준비 중 하나를 증명한다. 감시 만료를 기록하고 재가동하거나 sentinel/schedule에 인계한다. 독립 검토자를 쓸 수 없으면 UNKNOWN으로 남기고 자기 승인하지 않으며 다른 `READY`를 진행한다. 아니면 다음 안전 단계를 계속한다.
- 논스톱 연쇄(U146): 카드·PR·백그라운드 실행을 마쳐도 턴은 끝나지 않는다. 같은 턴에 `uaos coord next --project <루트> --tool <자기 도구> --claim`을 실행해 `NEXT`면 그 카드를 시작하고, `HANDOFF`면 담당 도구에 `uaos coord deliver`로 넘기며, `WAIT`·`HUMAN`·`DONE`일 때만 사람 전용 항목을 한 번에 모아 보고한다. 일정 정본은 메인 체크아웃의 `.coord/master_schedule.json`이고, Codex 판정 대기(REVIEW) 위에 쌓는 것은 3단까지다. 종료 관문은 세 도구 모두 Stop 훅의 `uaos coord stop-gate`다(U146-B: 세 도구 모두 전역 설치 훅 `--from-hook`, 프로젝트에 자기 Claude Stop 훅이 있으면 전역 훅은 비켜선다). 진척 없는 재진입은 한 번만 허용하고, 자기 상태가 LIMITED인 도구는 새 카드로 붙잡지 않는다(R7 예산). push 전에는 `uaos coord push-check --project <루트> --branch <브랜치>`가 ALLOW여야 한다.
- 병합 링크는 실시간 PR이 `OPEN`이고 병합 가능함을 확인한 뒤만 사용자에게 표시하며, 대체·폐쇄되면 같은 보고에서 즉시 밝힌다.
- 자가개선(RSI)은 증거만 만든다: `uaos rsi report` → `uaos rsi propose` → 시험 실행 → `uaos rsi gate --candidate <파일>`(참고 증거) → 릴리스는 `uaos rsi prepare` → `uaos rsi ship`(fetch·commit·push·PR, 자동병합 금지, 모든 외부 단계 실패는 fail-closed). 채택은 PLAN 카드와 검토된 커밋으로만 한다. 같은 계정 안의 이름표는 인증이 아니므로 `rsi adopt`로 자동 채택하지 않는다(B83). 평가기(테스트·장부·관문 코드)는 개선 대상이 아니다.
- 유료 LLM으로 크론·폴링을 돌리지 않는다: 변경 감시는 `uaos rsi schedule`(Windows 예약, 프로젝트별 고유 작업 이름, 기본 드라이런)이 로컬에서 결정적으로 돈다. 변화가 없으면(`ACK_ONLY`) 조용하고, 내용 해시가 실제로 바뀐 경우(`ACTIONABLE_DELTA`)만 한 번 모아서 고정 관문 PR 루프(`rsi prepare`/`rsi ship`)로 들어간다. 보존(`uaos rsi retention`)은 항상 드라이런 매니페스트이고, 삭제는 이 계획과 별도의 최신 승인이 있어야 한다.
- 복귀 도구는 우편함·복귀 체크리스트·대행 diff와 인수를 재검토한 뒤에만 지휘를 재개한다.
- 병합(U166, 2026-10-05 사용자 내규): PR 작성 도구가 아닌 판정 도구(Codex·Antigravity)의 우편함 편지가 그 head를 PASS/APPROVE했고 PR이 `OPEN`·`MERGEABLE`이면 `uaos coord merge --project <루트> --pr <번호> --head <sha> --verdict <relay_id>`가 1순위 Antigravity → 2순위 Codex에게 `gh pr merge --match-head-commit`을 맡기고, `gh pr view`가 MERGED를 보일 때만 성공으로 친다. 내 권한으로 못 하는 단계는 사용자에게 넘기지 않고 할 수 있는 다른 도구로 돌린다.
- 대기는 실패다(U166): 한 도구나 사용자를 30분 넘게 기다리는 단계(`VERDICT_REQUESTED=YES` 대기 편지, `master_schedule.json`의 HUMAN·REVIEW·BLOCKED·waiting_on; 사람 전용 목록을 적은 HUMAN 단계는 제외)는 3도구 각자의 프롬프트 훅이 `WAIT IS FAILURE`로 알리고 대신할 수 있는 ACTIVE 도구를 제안한다. 동의가 모여 `ADOPTED`·`REROUTED` 줄이 자기를 지목하면 그 도구가 같은 턴에 맡는다. 훅이 돈 도구마다 동의가 기록되어 다른 도구의 훅에 보이고, ACTIVE 도구 전원(빠진 도구·심장박동이 끊긴 도구 제외, 30분 지난 동의 무효)이 동의하면 메인 체크아웃 `.coord/master_schedule.json`에서 대기 단계가 그 도구 몫 READY로 재배정된다(대기 편지는 새 READY 단계). 대신할 도구가 없을 때만 BLOCKED를 기록하고 다음 카드로 간다. 확인: `uaos coord stall --project <루트> --tool <자기 도구>`.
- 티키타카(U172): 도구 사이 결정은 짧은 증거 턴(바뀐 것 + 묻는 것)을 `uaos coord deliver` 편지로 주고받아 한 결정당 최대 5턴 안에 AGREE·반대안·PASS로 끝낸다. 판정은 그 작업을 작성하지 않은 도구가 하고, 침묵한 도구는 U166대로 빠진 채 남은 ACTIVE 도구의 동의로 진행하며, 같은 원인으로 두 번 실패하면 경로를 바꾼다. 제안(U219): 어느 도구든 찾아낸 후속 작업을 사용자 클릭 카드나 "할까요?" 질문으로 남기지 않는다. 목표·허용 파일·통과 명령·멈춤 조건을 담은 `PROPOSAL` 편지로 조율자에게 `coord deliver`한다. 조율자는 PLAN·`master_schedule.json`에서 쓰지 않은 카드 번호, 단일 소유자, 중복을 먼저 확인하고, ACTIVE인 나머지 도구와 위 티키타카로 협의한다. LIMITED/ABSENT 도구는 기다리지 않고, 권한이 UNKNOWN이면 시작하지 않는다. AGREE가 나면 배정된 도구가 기존 단계 실행자나 영속 인계로 무승인 시작하고, 사용자에게는 결과만 보고한다. 목적은 토큰 예산 대비 최대 성과다(2026-10-18 사용자 지시).
- 멈추고 사용자에게 물을 것: 삭제, 병합(`uaos coord merge`의 모든 경로가 실패했을 때만)·배포·게시, 결제, 계정·권한·시스템 설정 변경. push는 사용자가 커밋한 상시 허가 `.coord/grants/push.json`(기능 브랜치만, main·강제 push·병합 제외; `expires_at`이 있으면 그 시각까지만, 오프셋 없는 시각·읽을 수 없는 값은 DENY)을 `uaos coord push-check`가 ALLOW할 때만 묻지 않고, 그 밖에는 묻는다.
