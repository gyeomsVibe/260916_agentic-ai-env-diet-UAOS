# U172 티키타카(tiki-taka): 3도구가 짧은 증거 턴으로 결정하는 법

마스터 스케줄 P4-A. Antigravity 동의 relay_b89b904a(2026-10-05), Codex는 UNKNOWN이라 U166에 따라 빠졌고 복귀 후 재검토한다.
이 문서는 추적되지 않던 `.coord/notes/U144_TIKI_TAKA_3TOOL_PIPELINE.md`(2026-10-03)를 대체한다. 옛 노트는 MIA 단계 수를 P3 이전 것으로 적었고, 아직 없던 장치를 약속했다.

## 1. 정의

티키타카는 Claude Code·Codex·Antigravity가 한 결정을 놓고 짧은 증거 턴을 `uaos coord deliver` 편지로 주고받는 방식이다.
한 턴은 "무엇이 바뀌었나(증거) + 무엇을 묻나(제안·반대안·판정 요청)" 하나다. 사용자는 편지를 나르지 않는다.

- 한 결정은 최대 5턴 안에 AGREE, 반대안 채택, PASS 중 하나로 끝낸다.
- 같은 원인으로 두 번 실패하면 경로를 바꾼다.
- 판정은 그 작업을 작성하지 않은 도구가 한다. 자기 작업을 자기가 승인하지 않는다.
- 침묵한 도구는 U166대로 빠지고, 남은 ACTIVE 도구의 동의로 진행한다. 빠진 도구는 복귀 후 재검토한다.

## 3. 이미 있는 장치

| 장치 | 하는 일 |
|---|---|
| `uaos coord deliver` | 편지를 우편함에 넣는다. 명시 `--wake-class`가 있으면 그것이, 없으면 본문이 깨움 여부를 정한다. |
| U120 자동 응답 | Antigravity에 간 실제 변화 편지는 헤드리스 Antigravity가 답한다. 하루 20회 상한, 넘친 편지는 대기열(backlog)로 가고 Antigravity 창이 직접 읽는다. |
| U143 소리 | 턴을 요구하는 편지가 오면 소리를 한 번 낸다(60초 묶음). |
| `uaos coord watch` | 0토큰 감시. 새 편지가 오면 끝나며 세션을 깨운다. 유료 모델 폴링을 쓰지 않는다. |
| U166 대기 실패 | 30분 넘는 대기를 실패로 보고, 각 도구의 프롬프트 훅이 동의를 모아 대신할 ACTIVE 도구에게 재배정한다. |
| `uaos coord next` | 메인 체크아웃의 `.coord/master_schedule.json`에서 다음 단계를 고른다(NEXT·HANDOFF·WAIT·HUMAN·DONE). |
| `uaos coord stop-gate` | 세 도구의 Stop 훅(U146-B). 할 일이 남았는데 턴을 끝내려 하면 막는다. |
| `uaos coord merge` | 판정 편지가 같은 head를 PASS했고 PR이 병합 가능하면 1순위 Antigravity, 2순위 Codex가 병합한다. |

## 4. MIA 11단계와의 관계

카드 파이프라인(U130/U170)은 [0. 사전 근거자료조사(웹딥리서치) → 1. 기획 → 2. 검증 → 3. 큰계획 → 4. 검증 → 5. 세부계획 → 6. 검증 → 7. 구현계획 → 8. 검증 → 9. 구현 → 10. 디버깅 및 최종검증] 순서다.
티키타카 턴은 주로 짝수 검증 단계(2·4·6·8)와 10단계에서 일어난다. 작성자가 제안하고, 작성하지 않은 도구가 반례나 PASS로 답한다.
9단계 구현의 기본 작업자는 Ollama 먼저, 다음 Antigravity, 그다음 Claude Code·`worker: apply`다.

## 5. 아직 열린 문제

- U169: 명시 `--wake-class ACTIONABLE` 편지가 본문 때문에 자동 응답을 못 받던 문제. 수정은 끝났지만 감사(audit) 행을 기다리며 병합 전이다.
- U123 감사 행: 커밋 관문은 `Audit: relay_<id>`가 장부의 ANSWERED 행과 맞는지만 보고, 실제 헤드리스 호출이었는지는 확인하지 않는다. Codex 재검토 대상이다.
