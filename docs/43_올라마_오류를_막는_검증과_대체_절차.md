# 올라마 오류를 막는 검증과 대체 절차

상태: 유지보수 지침, 2026-09-25. 올라마는 **유료 API 토큰을 쓰지 않는 전자계산기·유선 전화기**다. 로컬 추론 토큰·시간·전기는 사용하며, 자기 결과의 판정자가 아니다. 이 문서는 [UAOS 네 도구 운영 규칙](AI_4도구_아이디어_조사와_위임전_매뉴얼_운영규칙.md)과 전역 영문 정본 `shared/global-rules/core.md`의 실행 방법을 구체화한다.

## 실제로 발견한 세 가지 실패

| 작업 | 관찰 | 판정 |
|---|---|---|
| U28 첫 추출 | 입력에 없던 파일명을 만들어내고 용어를 오역했다 | 사실 검사 실패, 결과 폐기 |
| U28 매뉴얼 포함 재시도 | 여전히 존재하지 않는 파일명을 제시했다 | 같은 원인 2회, 더 넓은 재시도 중단 |
| U29 세 구절 복사 | 세 인용은 입력과 같았지만 요청한 순수 JSON 대신 코드 펜스를 붙였다 | 내용은 대조 가능, **형식 관문은 실패** |

이 표는 올라마가 언제나 틀린다는 뜻이 아니다. **맞는 문장과 틀린 형식이 동시에 나올 수 있다**는 실측이다. `exit 0`이나 모델의 자신감으로 합격시키지 않는다. 계정 한도 절감률은 대조 측정 전 `UNMEASURED`다.

## 호출 전: 입력을 축소하고 매뉴얼을 실제 전달

1. 한 번에 **동사 하나**만 요구한다. “프로젝트를 진단해” 대신 “입력의 세 문장을 그대로 복사해”처럼 쓴다. 요약이 필요하면 원문 행 번호를 먼저 붙인다.
2. 작업 프로세스 매뉴얼 파일에 작업 ID, 입력 파일·SHA-256, 허용 출력, 금지 행동, 시간 상한, 기계적 인수, 실패 중단 조건, 최종 판정자를 적는다. 입력 파일 해시를 호출 전에 계산하고 기록한다.
3. 매뉴얼 **경로만 프롬프트에 쓰지 않는다**. `olla ask -f <매뉴얼> -f <입력>`처럼 내용이 실제 요청에 포함되는지 확인한다. Antigravity도 `--prompt-file` 내용과 허용 자료가 실제 stage에 있는지 확인한다.
4. 사람이 새 파일명·설계·합격 판단을 요구하는 작업은 Ollama에 보내지 않는다. 그런 질문은 지휘자가 맡고, 필요한 좁은 계산만 분리한다.

## 응답 후: 결정적 관문

1. **형식**: 요청한 JSON이면 JSON 한 객체만 허용한다. 코드 펜스를 허용할 필요가 있다면 사전에 “바깥쪽 펜스 한 쌍만 제거”를 관문에 명시하고, 그 밖의 설명 문장은 거부한다. 이번 U29 관문은 펜스를 허용하지 않았으므로 실패로 남겼다.
2. **원문**: 인용은 입력의 연속된 문자열인지 직접 검사한다. 요약은 원문 줄과 숫자를 다시 대조한다. 없던 경로·명령·수치가 등장하면 즉시 거부한다.
3. **파일**: 출력이 파일명을 지목하면 경로가 허용 목록에 있고 실제 존재하는지 검사한다. 코드 수정이라면 변경 파일 집합과 고정 인수 테스트를 독립 확인한다.
4. **무결성**: 호출 전후 입력 해시를 비교한다. 결과가 없어도 `UNKNOWN`이지 성공이 아니다. 실패와 토큰·벽시계는 같은 `work_id`로 장부에 남긴다.
5. **재작업**: 같은 원인 두 번이면 프롬프트를 길게 늘리는 재시도를 멈춘다. 입력을 더 줄이거나 `rg`·JSON 파서 같은 결정적 도구로 전환한다. Ollama는 다음 작업 선택이나 승인 판단을 하지 않는다.

## 작은 사용 예시

`U29`에서 매뉴얼과 7줄 증거를 함께 보냈다. 세 문자열은 입력과 일치했지만 JSON 펜스가 붙었다. 따라서 “사실 3/3 일치”와 “형식 0/1”을 **따로** 기록한다. 이처럼 실패 이유를 분해해야 다음 RSI 실험에서 “더 긴 프롬프트”가 아니라 “형식 정규화 허용 범위”라는 작은 가설을 시험할 수 있다. 허용 범위를 바꿀 때는 기존 반례를 고정한 채 비교하고, 품질이 악화되면 채택하지 않는다.

세부 작업 계약과 결과는 [U29 카드](../.coord/tasks/U29-global-rule-deployment.md), [올라마 매뉴얼](../.coord/tasks/U29-ollama-global-rule-audit-manual.md)에 있다.

## U30 추가 반례와 적용 범위

2026-09-25 U30에서 사전 고정한 8개 검사를 대상으로 로컬 작업자에게 `olla_evidence.py` 구현을 맡겼다. 로컬 파일럿은 `PROVIDER_ERROR`로 끝났고 변경 파일은 0개였다. 원격 Antigravity로 같은 범위를 다시 시도했으나 `TIMEOUT_PARTIAL`·`promotion BLOCKED`였고 원본에 반영된 파일은 0개였다. 원격 단계의 부분 산출물은 격리된 `.work` 안에만 남겼다. 두 실행 모두 원장을 `ABANDONED`로 정리했다. 따라서 이 문서의 관문은 **운영 계약**이지, 자동 검증기 완성·테스트 통과 증거가 아니다.

이 반례를 반영해 세 지휘 도구의 전역 규칙에 다음 순서를 고정했다: 결정적 방법 검토 → 매뉴얼 발행·내용 전달 → 한 연산만 위임 → 출력 격리 → 원문·형식·경로·해시·고정 인수를 독립 검사 → 실패 기록 → 같은 원인 두 번이면 해당 경로 중단. 원격 재시도도 자동 권리가 아니며 예상 토큰·시간과 품질 관문을 먼저 따진다. 실제 비용 절감률은 `UNMEASURED`로 둔다. 관련 증거는 [U30 카드](../.coord/tasks/U30-ollama-evidence-gate-design.md)에 있다.
