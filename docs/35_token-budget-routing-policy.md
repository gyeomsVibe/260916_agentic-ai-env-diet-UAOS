# 3대 도구 토큰예산 예측·역할 전환 규칙

상태: 유지(maintained) 운영 규칙 v1, 2026-09-24. 이 프로젝트의 단일 계획(`.coord/PLAN.md`)과 `docs/01` §20에 종속된다. 실제 계정 한도 절감 효과는 대조 실험 전까지 `UNMEASURED`다.

## 1. 목표와 사실 경계

- 목표: Codex와 Claude Code의 희소한 사용량을 설계·인수·중요한 수정에 남기고, 단순 노동은 로컬 Ollama로 보낸다. Antigravity의 빈번한 총괄 대행으로 독립 검증이 사라지는 일을 막는다.
- Ollama는 사용자가 정의한 **“단순 추론·의지 없는 전자계산기, 전화기”**다. 호출하면 한정된 계산 결과를 내지만 목표·설계·성공 여부·다음 도구를 스스로 정하지 못한다.
- Windows PC의 로컬 Ollama 호출은 유료 API 토큰 0건으로 계측하되 전력·시간·하드웨어 비용이 0이라는 뜻은 아니다. 유료 토큰 대리지표, 계정 사용량 변화, 품질, 벽시계 시간을 별도 장부에 적는다.
- OpenAI는 비슷한 요청도 모델·문맥·추론·도구·검색·캐시 때문에 사용량이 달라진다고 명시한다. 계정의 5시간/주간 잔여율을 토큰 수로 환산하지 않는다. [공식 사용량 설명](https://learn.chatgpt.com/docs/pricing)
- Claude의 `/usage`는 구독 사용량 막대와 세션 토큰을 구분한다. 세션의 추정 달러값은 구독 청구액이 아니다. [Claude 공식 비용 안내](https://code.claude.com/docs/en/costs)

## 2. 한 작업 시작 전 예산 장부

지휘자는 작업 카드에 `work_id`, 단일 작성자, 위험도, 인수 명령, 필요 판정자를 먼저 적는다. 작업 경계를 넘길 때만 아래 표를 갱신한다. 유료 모델을 주기적으로 깨우는 상태 폴링은 금지한다.

| 필드 | Codex | Claude Code | Antigravity | Ollama |
|---|---|---|---|---|
| 현재 용량 | 앱 `get_usage_limits`의 5시간·주간 `usedPercent`, 재설정 시각 | `/usage` 또는 계정 화면의 실제 잔여율·재설정 시각 | 제공자가 확인한 잔여율·재설정 시각; 없으면 `UNKNOWN` | 로컬 서비스/모델 가용성 |
| 이번 실행 | 시작/종료 사용량 스냅샷과 출력 토큰 대리지표 | `/usage` 세션 입력·출력·캐시 및 계획 막대 변화 | CLI 결과의 입력·출력·캐시·벽시계 | `olla` 사용량 기록, pilot `summary.json`의 로컬 입력·출력·벽시계 |
| 신뢰도 | 같은 창 안의 전후 스냅샷 | 같은 계정·같은 창의 전후 스냅샷 | 원본 실행 영수증 | 인수 게이트와 원본 해시 |

다른 작업이나 재설정이 중간에 끼면 사용량 차이는 해당 작업의 비용으로 쓰지 않고 `CONTAMINATED`로 기록한다. 공급자마다 퍼센트·토큰·캐시 계산이 다르므로 수치를 합산하지 않는다. 실제 한도가 조회되지 않으면 `UNKNOWN`으로 두고 사용자가 전에 말한 3% 같은 오래된 스냅샷을 현행 값으로 재사용하지 않는다.

## 3. 예측식과 안전 여유

각 공급자·모델·작업 유형별로 동일한 기준의 유효한 전후 샘플만 모은다. 샘플이 3개 이상이면 최근 10개까지의 작업당 사용량 증가폭(`after.usedPercent - before.usedPercent`)에서 보수적인 80백분위수를 다음 단계 예상 소모량으로 둔다. `n=3`은 예측을 시작하기 위한 최소 표본이고, 80백분위수는 평균보다 큰 작업을 준비하기 위한 초기 정책값이다. 두 값 모두 실측 정확도가 확인된 최적값은 아니며 10개 누적 후 재평가한다.

`예상 종료 잔여율 = min(5시간 잔여율 - 5시간 예상 소모량, 주간 잔여율 - 주간 예상 소모량)`이다. 예약량은 각 창별로 `max(직전 중요 판정 3건의 최대 소모량, 5%p)`로 잡는다. `5%p`는 표본이 없을 때 판정 1회를 보존하기 위한 임시 안전값이며 성공률 검증 전에는 줄이지 않는다. 표본 3개 미만, 계정 창 누락, 다른 작업의 소비 혼입, 도구 상태 오래됨이면 예상값은 `UNKNOWN`이다. 실제 토큰 수만으로 퍼센트 감소를 예측하지 않는다.

작업 착수 관문: 예상 종료 잔여율이 예약량보다 높고, 한 번의 재작업·독립 검증을 수행할 여유가 있을 때만 새 유료 구현 단계를 연다. 불확실하면 작업을 더 작은 계약으로 쪼개고 Ollama·결정적 스크립트로 준비한다. P1 복구와 사용자 승인 대기는 절약을 이유로 무시하지 않는다.

## 4. 역할 전환: 품질이 한도보다 먼저

1. **평상시**: Codex는 계획·작업 카드·최종 판정, Claude는 제한된 구현 또는 독립 검토, Antigravity는 별도 관측 경로의 검증, Ollama는 단순 계산·형식 변환·정확한 편집을 맡는다. 같은 파일을 동시에 쓰지 않는다.
2. **Codex 예산 부족 예측**: Codex는 새 장문 탐색·구현을 멈추고, 이미 정의된 작업의 판정 예산을 보존한다. Claude가 가용하면 부지휘자로 1회 인계한다. 인계는 한도 상태 전이당 한 번이며 매 작업마다 반복하지 않는다.
3. **Claude 예산 부족 예측**: Claude는 핵심 구현·독립 반례 검토용 예약량을 남기고, 로그·요약·기계적 패치는 Ollama로 보낸다. `/usage`가 `UNKNOWN`이면 절약 모드를 택하되 부재로 단정하지 않는다.
4. **Codex와 Claude 둘 다 실제로 제한·부재**: 기존 사용자 위임에 따라 Antigravity가 임시 조율자가 된다. 원본 계획·카드에 이유, 인계 시각, 범위, 승인 경계를 기록한다. 사용자 승인 대상은 대행으로 풀리지 않는다.
5. **Antigravity 총괄 대행의 종료**: 두 지휘 도구 중 하나가 돌아오면 새 단계의 총괄 권한은 되돌린다. 대행 동안의 결론은 작성자 자기 판정만으로 확정하지 않고 복귀한 지휘자가 diff·인수·원장을 재검토한다.

잔여율이 낮다는 이유만으로 Antigravity를 무조건 총괄로 올리지 않는다. 범위가 모호하거나 설계 판단이 필요한 단일 과제에는 Antigravity를 **범위가 정해진 작업자**로 쓸 수 있지만, 동시 검증자 역할을 겸할 수 없다. 읽기 전용 자문 1회와 원격 구현 1회를 각각 별도 예산에 넣는다. 한 번의 원격 호출이 직전 동형 작업의 입력 토큰 또는 벽시계의 3배를 넘으면 비용 게이트 실패로 기록하고 계약을 축소한다. 과거 U20의 565k 원격 구현과 U23 광범위 호출의 823k/변경 0건이 이 제한의 직접 근거다.

## 5. Ollama 전화기 사용 계약

각 도구는 반복·형식·발췌·좁은 패치를 시작하기 전에 로컬 호출 가능성을 판정한다. 명령서에는 **한 목표, 입력 파일과 SHA-256, 허용 출력 경로, 정확한 SEARCH/REPLACE 또는 추출 규칙, 시간·출력 상한, 금지 작업, 결정적 인수 명령**이 들어가야 한다. 현행 프로젝트의 구체성 80점은 지시문의 완전성 관문이지 모델의 성공 보증이 아니다. 판단·승인·원격 전송·원본 직접 수정은 Ollama에게 맡기지 않는다. Ollama 결과가 없거나 인수가 실패하면 성공으로 기록하지 않는다.

Ollama는 동일 작업을 무제한 재시도하지 않는다. 첫 실패는 원인을 분류하고 프롬프트를 좁힌 뒤 1회만 재시도한다. 같은 원인 3회면 중단한다. `--worker auto`의 자동 원격 승격은 작업 카드가 원격 최대 비용과 허용 경로를 명시한 경우에만 사용한다. 그렇지 않으면 `--worker local`을 명시하고 원격 승격은 지휘자가 새 계약으로 결정한다.

## 6. 품질 관문과 U23 선행 위험

- 인수 테스트는 작업자에게 공개한 예제만 반복하지 않는다. 파일 해시·범위 밖 변경·실제 Windows 병렬 실행·실패 경로를 독립 확인한다. 변경 작성자가 유일한 검증자가 될 수 없다.
- 비용이 줄어도 P1 또는 거짓 PASS가 있으면 작업은 `REWORK`다. `DONE`으로 올리지 않는다.
- 2026-09-24 Codex 반례: `mailbox.recover_stale_claims()`가 `evt_alpha_beta`를 `evt`로 복구했고, 같은 초의 두 감시 사이클은 `MailboxRejected`로 중단됐다. U23의 과거 `DONE` 보고는 이 반례가 해결될 때까지 인수 보류다. 우편함의 “100% 무손실”과 “24/7 안정”은 현재 보증하지 않는다. 이 설계는 복구된 U23을 필요조건으로 삼지 않고 작업 카드·원장 파일을 유지한다.

## 7. 매 작업 데이터와 개선 주기

`olla` 사용량 로그와 pilot 요약에서 `work_id`, 호출자, 모델, 작업 유형, 프롬프트 해시, 허용 파일 해시, 로컬 입력·출력 토큰, 벽시계, 종료코드, 인수 결과, 원본 변경 집합, 승격 이유를 추출한다. 원문 프롬프트·비밀·토큰 값은 장부에 복사하지 않는다. 한 작업의 결과가 누락되면 `UNKNOWN`이다. Codex·Claude·Antigravity도 같은 작업 ID로 각자 사용량 스냅샷을 남긴다.

10건의 유효 표본마다 유형별 성공률, 재작업률, 50/80백분위 벽시계, 원격 승격률, 지휘 도구의 5시간/주간 잔여율 변화, P1 수를 검토한다. 새 규칙을 기존 경로와 같은 기준선·같은 숨은 인수로 비교하고 품질이 낮아지면 절감 정책을 채택하지 않는다. 샘플 부족이나 계정 사용량 부재면 효과를 `UNMEASURED`로 유지한다. 로컬 사용량 200,133토큰은 로컬 연산량이며 유료 계정에서 200,133토큰을 절약했다는 뜻이 아니다.

## 8. 참고 프로젝트에서 채택·기각한 것

- `260713_pc-optimization`: 적용 전 백업과 복구 검증 원칙을 채택. 토큰 절감 실측 자료는 찾지 못했다.
- `260714_gyeoms-ai-agent`: 회귀·진단 관문을 참고. 이 프로젝트에서도 직접 비교 가능한 토큰 예산 자료는 찾지 못했다.
- `260718_agentic-ai-platform-optimization`: C3P 비대칭 예산·무비용 대기 구상을 참고. 과거 문서의 75~85% 절감·자동 승계 수치는 이 프로젝트에서 검증되지 않아 채택하지 않는다.
- `260823_codex-3p-orchestrator`: [해체 결정](../../260823_codex-3p-orchestrator/docs/C3P_RETIREMENT_DECISION.md)의 비대해진 조율, 미검증 85% 주장, 승인 상속 문제를 재발 방지 조건으로 채택. 이 프로젝트는 퇴역 Bridge를 복구하지 않는다.
- `260912_multi-party-ai-agent-real-time-orchestration-mcp`: `docs/23`의 한 계획·한 작성자·검증 뒤 종결 규칙을 채택. 그 프로젝트의 역할/상태를 이 프로젝트의 현행 PLAN보다 우선하지 않는다.
- 이 프로젝트 `docs/26`: Ollama 372회·로컬 200,133토큰·U23 7단계 315.9초라는 작성 시점 기록을 원장 대조 대상으로 사용. U23 최종 품질 판정의 근거로 단독 사용하지 않는다.
