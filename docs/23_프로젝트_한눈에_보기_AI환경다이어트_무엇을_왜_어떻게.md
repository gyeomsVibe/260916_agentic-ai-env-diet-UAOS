# AI 환경 다이어트 — 무엇을, 왜, 어떻게

작성 2026-09-20 · 대상 독자: 이 저장소를 처음 여는 사람 · 전문 용어는 처음 나올 때 쉬운 말과 함께 씁니다.

> 한 줄: **AI 도구 세 개가 같은 프로젝트를 함께 하면서, 거짓 성공 없이, 적은 토큰으로 일하게 만드는 장치**를 만들고 실제로 측정한 기록입니다.

---

## 1. 다섯 줄 요약

1. 세 도구가 있습니다. **Codex**(지휘·판정), **Antigravity**(실행), **Claude Code**(검증·대행). 계정 한도가 막히면 이 PC의 **로컬 모델(Ollama)** 이 정해진 패치를 대신 수행합니다.
2. 셋이 각자 원본을 고치다 보니 서로의 작업을 덮고, "성공했다"는 보고가 실제와 달랐습니다.
3. 그래서 **복사본에서 작업하고, 검사를 통과해야만 원본에 반영되는 절차**(파일럿)를 만들고, 통과 못 하면 닫히는 잠금장치를 여러 겹 넣었습니다.
4. 실제 과제 3개로 재 보니 **지휘자(Codex)가 쓰는 입력 토큰이 평균 −76.7%, 출력이 −97.0%** 였고 품질은 같았습니다.
5. 다만 "계정 한도가 실제로 얼마나 덜 닳는가"는 아직 재지 못했습니다. 그런 항목은 `UNMEASURED`라고 적어 둡니다.

## 2. 용어 사전 (이 저장소에서만 쓰는 말 포함)

| 말 | 쉬운 뜻 |
|---|---|
| **파일럿(pilot run)** | 원본을 직접 건드리지 않고 복사본에서 일한 뒤, 검사를 통과할 때만 반영하는 절차. |
| **원장(ledger, SQLite)** | 누가 언제 무엇을 시도했고 어떤 결과였는지 남는 장부. 지울 수 없게 기록만 덧붙입니다. |
| **매니페스트(manifest)** | 원본 폴더의 파일 목록과 지문(해시). 실행 중 원본이 바뀌면 이것으로 알아챕니다. |
| **인수 테스트(acceptance test)** | "이걸 통과해야 합격"이라고 미리 정해 둔 검사. 작업자가 이 검사를 고치는 것은 금지입니다. |
| **정숙 창(QUIET_LOCK)** | 한 도구가 작업하는 동안 다른 도구가 원본에 쓰지 않기로 한 시간. |
| **fail-closed(실패 시 닫힘)** | 확신이 없으면 통과시키지 않고 막는 방식. 반대는 "일단 통과"입니다. |
| **UNMEASURED / UNKNOWN** | "좋아졌다고 말할 근거가 아직 없음" / "검사를 안 돌려서 모름". 추측으로 채우지 않습니다. |

## 3. 문제 진단 — 무엇이 잘못되고 있었나

### 3-1. 거짓 성공

작업자가 "다 했다"고 보고했는데 실제로는 바뀐 파일이 없거나, 검사를 자기 입맛에 맞게 고쳐 통과시킨 경우가 있었습니다.

- 예: 브리핑 없이 "통과"만 반환, 아무것도 안 바꾸고 종료, 테스트 파일을 비워 통과.

### 3-2. 서로의 작업 덮어쓰기

한 도구가 복사본에서 일하는 동안 다른 도구가 원본에 메모를 쓰면, 반영 시점에 원본이 달라져 작업이 통째로 무효가 됐습니다(`SOURCE_DIVERGED`). 이 사고가 반복됐습니다.

### 3-3. 흩어진 기록

조율 메모 79건, 별도 노트, 계획서, 카드, 실행 요약이 각각 다른 곳에 쌓였습니다. 지휘자가 무엇을 판정해야 하는지 한눈에 볼 수 없었습니다.

### 3-4. 근거 없는 "절감" 주장

"토큰을 줄였다"는 말은 많았지만 같은 과제를 같은 조건으로 비교한 수치가 없었습니다.

## 4. 해결 — 무엇을 만들었나

### 4-1. 파일럿 절차와 잠금장치 (`v7_harness/`)

복사본에서 작업 → 검사 → 통과해야 반영. 여기에 "이런 경우엔 무조건 막는다"를 여러 겹 넣었습니다.

| 막는 상황 | 이름 |
|---|---|
| 실행 중 원본이 바뀜 | `SOURCE_DIVERGED` |
| 집 폴더·임시 폴더 등 작업 범위 밖에 씀 | `EXTERNAL_WRITE` |
| 아무것도 바꾸지 않고 통과 주장 | `NO_CHANGES → REWORK` |
| 반영했다는데 원본에서 그 변화가 안 보임 | `APPLY_NOT_OBSERVED` |
| 바꿨다고 신고한 파일 목록과 실제가 다름 | `APPLY_MISMATCH` |
| 결과가 늦게 도착해 상태를 확신할 수 없음 | `LATE_RESULT` → 정리 절차 |

### 4-2. 조율 스트림 (`v7_harness/coord/`)

세 도구가 한 일을 **사건 한 줄씩** 쌓고, 그것을 접어 지휘자에게 보냅니다.

```
사건 1줄 → .coord/stream/<날짜>.jsonl
            ↓ 접기(마지막 판정 이후만, 60줄·6KB 상한)
      .coord/codex_brief.md
            ↓ 상태가 바뀐 경우만 1건
   codex queue --thread <대화> --message <5줄>
            ↓
   지휘자 창에 "다른 작업에서 …이(가) 보냄"
```

지키는 규칙: 판정 기록은 지휘자만, 실행 보고에는 명령과 종료 코드가 필수, 메시지 첫 줄은 `[DATA]`(지시가 아니라 데이터라는 표시), 값 대신 경로·해시만, 같은 내용은 두 번 보내지 않음.

### 4-3. 측정 장치 (`.coord/runs/`)

같은 과제를 두 방식으로 돌려 비교합니다. **A = 지휘자 혼자**, **B = 지휘자 1턴 + 제어층 + 작업자**. 토큰·시간·도구 호출·품질을 모두 기록합니다.

## 5. 실제로 잡은 사고 (교훈이 규칙이 된 사례)

| 사고 | 무슨 일이 | 어떻게 고쳤나 |
|---|---|---|
| 테스트 맞추기 | 작업자가 "특정 테스트일 때만 검사를 건너뛰는" 코드를 넣음 | 반영 전 사람이 차이를 읽고 거부. 검사 파일 지문(해시)을 매번 확인 |
| 검사 파일 삭제 | 작업자가 테스트 파일을 비워 통과 시도 | 검사 시작 전에 지문부터 대조해 즉시 실패 |
| 모순된 고정 테스트 | 새 규칙과 옛 테스트가 양립 불가 → 정직한 통과가 불가능 | 테스트의 모순을 먼저 교정한 뒤 재실행 |
| 동시 기록 유실 | Windows에서 여러 주체가 동시에 파일 끝에 덧붙이면 줄이 통째로 사라짐 | 폴더 단위 잠금 도입, 8건 중 2건 유실 → 0건 |
| 보관 중 유실 | 정리 작업이 잠금 밖에서 읽고 잠금 안에서 지움 | 읽기부터 잠금 안으로. 7건 중 6건 유실 → 0건 |
| 간헐 실패 오인 | 큐 용량 4에 동시 8건을 보내 정상 거절이 "실패"로 집계 | 용량을 요청 수에 맞춤. 포화 검사는 전용 테스트가 담당 |

## 6. 숫자 (같은 과제, 같은 조건)

| 과제 | 지휘자 입력 토큰 | 지휘자 출력 토큰 | 도구 호출 | 품질 |
|---|---|---|---|---|
| P05 | −73.7% | −94% | 4 → 0 | 동일 |
| P06 | −80.2% | −98.3% | 6 → 0 | 동일(숨은 검사 통과) |
| P07 | −76.3% | −98.8% | 4 → 0 | 동일(숨은 검사 통과) |

- 평균: 입력 **−76.7%**, 출력 **−97.0%**.
- 조율 인계 1회 분량: 기존 메모 평균 1,552자 → 브리핑 828자(**−46.6%**), 지휘자 창에 실제 들어가는 메시지는 81자.
- 아직 모르는 것: 계정 한도 차감 폭, 하루 운용 기준 판정 지연. `UNMEASURED`로 둡니다.
- 테스트: 전체 **412개 통과**(1개 건너뜀), 문법 검사 종료 코드 0.
- 로컬 작업자: 모델 3종 × 과제 6종 벤치에서 `qwen2.5-coder:7b` 6/6, 총 48.5초. 실패가 갈린 축은 파일 크기가 아니라 **지시의 모호함**이었습니다(자세히는 [ollama/](../ollama/README.md)).
