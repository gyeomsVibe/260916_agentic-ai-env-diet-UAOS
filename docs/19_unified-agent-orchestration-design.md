# Codex–Antigravity 단일 계획 조율 설계

상태: `APPROVED-DESIGN`  
결정: `GO`  
적용 범위: 이 프로젝트의 Codex 및 Antigravity 작업

## 1. 결정 요약

Codex와 Antigravity를 두 개의 독립 작업자로 운영하지 않는다. Codex가 하나의 마스터 계획과 단계 순서를 소유하고, 실제 수행은 프로젝트 내부의 단계별 전용 대화창에서 단일 소유자가 맡는다. Antigravity의 실행은 Codex 프로젝트에 속한 해당 단계 전용 대화창의 실행으로 간주한다.

이 설계가 보장하려는 것은 다음 네 가지다.

- 계획은 하나다.
- 한 단계의 활성 소유자는 하나다.
- 한 단계의 수행 대화창은 하나다.
- 다음 단계는 현재 단계의 검증이 끝난 뒤 열린다.

## 2. 문제와 성공 기준

### 관찰된 문제

- 여러 도구가 같은 목표를 서로 다른 계획으로 재해석하면 범위와 우선순위가 갈라진다.
- 같은 작업 공간을 동시에 수정하면 변경 출처와 책임을 추적하기 어렵다.
- 대화만으로 인계하면 결정, 검증 결과, 미해결 위험이 다음 대화에 안정적으로 전달되지 않는다.
- 에이전트의 “완료” 선언과 실제 인수 조건 충족은 같지 않다.

### 성공 기준

- 어느 시점에도 활성 단계별 소유자가 정확히 한 명이다.
- 모든 변경은 `[U##]` 단계와 작업 카드로 역추적된다.
- 후속 단계는 선행 단계가 `DONE`이 되기 전에는 `ACTIVE`가 될 수 없다.
- 각 `DONE`에는 재현 가능한 검증 명령, 종료 코드, 결과가 있다.
- Codex와 Antigravity가 서로 다른 계획 사본을 유지하지 않는다.

### 비목표

- 범용 프로젝트 관리 제품을 만드는 것
- 모든 일을 여러 에이전트에게 병렬 분배하는 것
- 에이전트 간 자유로운 실시간 채팅을 동기화하는 것
- 검증 없이 에이전트 보고를 자동 승인하는 것

## 3. 단일 원본 구조

규칙의 정본은 이 문서다. `AGENTS.md`와 `.agents/rules/unified-codex-antigravity.md`는 각 도구가 이 정본을 발견하도록 하는 얇은 어댑터다.

실행 단계에서는 아래 구조를 사용한다.

```text
.coord/
  PLAN.md                 # 목표, 순서, 현재 단계, 결정 로그
  tasks/
    U01-<slug>.md         # 단계별 작업 카드
    U02-<slug>.md
  events.jsonl            # 선택: 추가 전용 상태 이력
```

`PLAN.md`는 Codex 조율자만 수정한다. 작업 카드는 현재 소유자가 수행 기록을 쓰고, Codex가 검토 결과와 최종 상태를 쓴다. 동적 잠금이나 실행 로그는 기본적으로 커밋하지 않는다.

## 4. 대화창과 접두어 규칙

접두어는 `[U##]` 하나로 통일한다.

- `U`: Unified plan
- `##`: 마스터 계획의 고정된 두 자리 순번
- 예: `[U01] 요구사항 고정`, `[U02] API 구현`, `[U03] 회귀 검증`

총괄 대화창은 계획·배정·검토·승인만 담당한다. 실제 조사, 편집, 테스트, 수정은 해당 `[U##]` 전용 대화창에서 한다. 한 단계가 재작업될 때 새 대화창을 만들지 않고 같은 단계 대화창을 이어간다. 컨텍스트 손상으로 교체가 필요하면 새 창은 `[U##-R1]`처럼 리비전을 붙이고, 기존 카드에 교체 이유와 인계를 먼저 기록한다.

## 5. 역할과 권한

| 역할 | 소유권 | 허용 작업 | 금지 작업 |
|---|---|---|---|
| 사용자 | 목표와 고위험 승인 | 범위 변경, 승인, 최종 우선순위 결정 | 없음 |
| Codex 조율자 | 마스터 계획과 게이트 | 분해, 순서 지정, 작업창 생성, 배정, 검토, 상태 전환 | 단계 구현을 총괄창에서 대신 수행 |
| 단계 소유자 | 배정된 `[U##]` | 배정 범위 수행, 자체 검증, 인계 작성 | 범위 확장, 다음 단계 시작, 직접 `DONE` 처리 |
| Antigravity | 배정된 단계의 실행자 | 전용 대화창에서 단계 수행 | 독립 마스터 계획 생성, 미배정 단계 수행 |
| 검토자 | 인수 증거 | diff·테스트·인수 조건 확인 | 구현자의 설명만으로 승인 |

Codex가 단계 소유자가 될 수도 있지만, 그 경우에도 총괄 대화창과 수행 대화창을 분리한다. 계획 권한과 실행 컨텍스트를 섞지 않는 것이 핵심이다.

## 6. 상태 기계

```text
BACKLOG -> READY -> ACTIVE -> REVIEW -> DONE
                    |          |
                    v          v
                  BLOCKED <- READY (재작업)
```

- `BACKLOG`: 정의됐지만 선행 조건이 남아 있음
- `READY`: 인수 조건, 범위, 소유자가 정해져 시작 가능
- `ACTIVE`: 소유자가 점유해 수행 중
- `REVIEW`: 수행자가 인계했고 검토 대기 중
- `DONE`: Codex가 증거를 확인해 종료
- `BLOCKED`: 사용자 결정, 권한, 외부 의존성 또는 반복 실패로 진행 불가

허용되는 핵심 불변식은 다음과 같다.

1. `ACTIVE` 단계마다 `owner`, `conversation`, `scope`, `started_at`이 존재한다.
2. 한 작업 카드에는 동시에 한 소유자만 존재한다.
3. 기본 실행 폭은 `WIP=1`이다.
4. 선행 단계가 모두 `DONE`일 때만 `READY`가 될 수 있다.
5. 수행자는 `REVIEW`까지만 전환하며 `DONE`은 조율자가 결정한다.
6. 같은 원인의 실패가 세 번 반복되면 추가 시도 대신 `BLOCKED`와 증거를 기록한다.

## 7. 작업 카드 계약

각 카드에는 최소한 다음 필드가 있어야 한다.

```markdown
# [U01] 단계 제목

- Status: READY
- Owner: antigravity | codex
- Conversation: [U01] 단계 제목
- Depends on: none | U00
- Scope: 허용 파일·자원
- Excludes: 명시적 비범위
- Outcome: 관찰 가능한 결과
- Acceptance: 검증 가능한 인수 조건
- Verification: 실행할 명령 또는 검토 방법

## Decisions
## Work log
## Handoff
- Result:
- Changed:
- Checks and exit codes:
- Remaining risks:
- Next action:
```

인계가 유효하려면 수신자인 Codex가 카드와 증거를 읽고 `REVIEW` 수신을 확인해야 한다. 메시지를 보냈다는 사실만으로 인계가 완료되지는 않는다.

## 8. 실행 프로토콜

### 계획

1. Codex가 목표, 비목표, 인수 기준을 고정한다.
2. 결과 단위로 단계를 나누고 순번 `[U##]`을 부여한다.
3. 각 단계의 의존성, 수정 범위, 소유자, 검증 방법을 기록한다.
4. 첫 단계 하나만 `READY`로 둔다.

### 수행

1. Codex가 프로젝트 안에 카드와 동일한 이름의 전용 대화창을 만든다.
2. 소유자는 카드와 정본 규칙을 읽고 `ACTIVE`로 점유한다.
3. 범위 안에서 작업하고 실행 증거를 남긴다.
4. 결과를 카드에 기록하고 `REVIEW`로 반환한다.

### 검토 및 다음 단계

1. Codex는 구현자의 요약이 아니라 작업 카드, 실제 diff, 검증 결과를 확인한다.
2. 기준 충족 시 `DONE`, 보완 가능하면 같은 창을 `READY`, 외부 결정이 필요하면 `BLOCKED`로 전환한다.
3. `DONE` 뒤에만 다음 순번을 `READY`로 바꾸고 새 전용 대화창을 연다.

## 9. 병렬화 예외

기본은 계획 순서대로 `WIP=1`이다. 아래 조건을 모두 만족할 때만 Codex가 병렬 단계를 허용할 수 있다.

- 선행 조건이 서로 독립적이다.
- 파일과 Git 작업트리의 쓰기 범위가 겹치지 않는다.
- 데이터베이스, 포트, 캐시, 생성물, 외부 계정 등 런타임 자원이 분리돼 있다.
- 각 단계에 별도 카드, 전용 대화창, 단일 소유자가 있다.
- 합류 순서와 통합 검증 단계가 미리 정의돼 있다.

하나라도 증명되지 않으면 직렬화한다.

## 10. 충돌과 복구

- 범위 충돌: 둘 다 중지하고 Codex가 카드 범위를 다시 나눈다.
- 계획 충돌: 작업 카드보다 `PLAN.md`, `PLAN.md`보다 사용자 최신 지시가 우선한다.
- 소유권 충돌: 기존 `ACTIVE` 소유자를 유지한다. 깨끗한 인계 또는 명시적 회수 전에는 탈취하지 않는다.
- 대화 손실: 카드의 Handoff를 기준으로 `[U##-R1]` 창을 만들고 이전 창을 폐기 상태로 남긴다.
- 반복 실패: 동일 원인 세 번이면 자동 재시도하지 않고 증거와 선택지를 사용자에게 보고한다.
- 조율자 부재: 새 Codex 조율자는 `PLAN.md`와 카드들을 읽고 현재 상태를 복원한 뒤에만 배정한다.

## 13. 최소 실험과 다음 결정

첫 실험은 자동화 도구를 설치하지 않고 세 단계짜리 실제 작업에 이 규칙을 적용한다.

1. Codex가 `.coord/PLAN.md`와 세 작업 카드를 만든다.
2. 한 단계는 Codex, 한 단계는 Antigravity에 배정하되 항상 직렬로 실행한다.
3. 각 단계에서 소유권 충돌 수, 재작업 수, 누락된 인계 필드, 검증 실패를 기록한다.

성공 임계치는 소유권 충돌 0건, 무카드 변경 0건, 검증 증거 누락 0건이다. 통과하면 카드 생성·상태 전이를 스크립트나 MCP로 자동화하고, 실패하면 규칙을 늘리기 전에 실패한 필드만 보강한다.

## 14. 컨텍스트·의도·검증 규칙

- 컨텍스트는 많을수록 좋다는 가정을 버린다. 항상 로딩하는 것은 사용자 목표, 현재 승인 경계, 활성 카드뿐이다.
- 단계에는 허용 범위, 인수 기준, 직접 의존 결정만 넣고 과거 로그·완료 단계·폐기 설계는 기본 제외한다.
- 참조 자료에는 권위, 범위, 작성일, 만료, 대체 문서를 기록한다. 오래된 자료는 현재 규칙보다 우선하지 않는다.
- 코드와 별도로 요구사항, 의도적 결정, 근거, 추측, 폐기 조건을 intent ledger에 보존한다.
- 완료는 실행자의 설명이 아니라 테스트, 시나리오, diff, 해시, 외부 receipt 중 적합한 증거로 판정한다.
- 검토 깊이는 위험에 비례한다. 저위험은 결정적 검사, 중위험은 위험 diff와 회귀 시나리오, 고위험은 전체 검토와 사용자 게이트를 사용한다.

## 15. 간결 보고와 자동 진행

- 사용자 보고는 결과, 변경, 검증, 잔여 위험, 다음 자동 행동만 우선 제시한다. 긴 로그와 조사 전문은 파일이나 카드에 보존하고 기본 출력하지 않는다.
- 사용자가 해야 할 일이 없으면 행동을 요청하지 않는다. 단계가 `DONE`이면 Codex가 다음 `READY` 단계의 `[U##]` 대화창을 열어 진행한다.
- 정상적인 범위 안 조사·편집·테스트·재작업은 추가 승인 없이 수행한다.
- 목표나 범위를 바꿔야 하거나 삭제·덮어쓰기·push·배포·결제·계정/권한/자격증명 변경이 필요할 때만 사용자 결정을 요청한다.

## 16. 계산기 원칙

- 계층: 지휘자(Codex·Claude Code, 가장 비쌈) → Antigravity(계정 한도가 드는 하인) → Ollama(이 PC, 한도 없음). 아래 계층이 할 수 있는 일은 위 계층이 하지 않는다. 사람이 손으로 계산하지 않고 계산기를 쓰는 것과 같다.
- 지휘자의 몫: 지시문(바꿀 파일·함수·값을 구체적으로), 숨은 인수 테스트(`.work/<과제>/accept_*.py`, 먼저 Red 확인), diff 검토와 `--approve` 판정. 코드는 손으로 쓰지 않는다.
- 배정: `pilot run --worker auto`. 지시 구체성 점수(`adapters/worker_advice.py`)가 60 이상이면 cascade(Ollama 먼저, REWORK 또는 로컬 실패 `PROVIDER_ERROR`·`TIMEOUT`·`EXECUTION_ERROR`면 Antigravity로 1회 승격), 미만이면 Antigravity. 요약의 `routed_by`에 배정 근거를 남긴다.
- Antigravity의 계산기: Antigravity가 IDE에서 직접 일할 때도 요약·변환·반복 편집·테스트 틀·로그 분류는 `pilot run --worker local` 또는 `olla ask -f <파일> --model qwen3.5-32k`로 Ollama에 먼저 넘기고, 결과는 원문 대조로만 채택한다.
- 관문: `.githooks/commit-msg`가 `python -m v7_harness.calculator_gate`를 불러, 커밋에 오른 `v7_harness/` 아래 `.py`가 APPLIED pilot 결과물과 내용이 다르면 커밋을 막는다. pilot이 막힌 경우의 예외는 커밋 메시지의 `Calculator-Exempt: <이유>` 한 줄로만 허용하고 이유가 기록에 남는다.
- 측정: 작업자별 토큰은 요약의 `agy_usage`로 남긴다. 지휘자 쪽 실제 한도 절감은 직접 측정 전까지 `UNMEASURED`로 기록한다. 실측(2026-09-23): U19 Antigravity 77k 토큰·85초 PASS, U20 자문 138k+구현 565k 토큰, U21a 로컬 7b 600초 `PROVIDER_ERROR` → Antigravity 335k 토큰 PASS.

## 17. 올라마(Ollama) '토큰예산절약용 일꾼' 영구 고정 및 권한 위임 체계

(2026-09-23 사용자 고정 지정)

- 정의: 올라마는 3대 프론티어 AI(Codex, Claude Code, Antigravity)의 유료 API 토큰 예산을 철저히 방어·보존하기 위한 비용 0원의 프로그래머블 단순 노동 일꾼(전자계산기)이다.
- 4대 불변식:
  1. **판정권 배제 (Verdict Invariant)**: 일꾼은 설계, 전략적 가치 판단, 성공/실패 판정 권한이 일절 없다. 판정은 오직 결정론적 인수 테스트(Acceptance Gate)와 지휘자 검증 관문만이 내린다.
  2. **단순 반복 노동 우선 위임 (Mandatory Rote Offloading)**: 대형 파일 구조 요약(`local_read_map`, `olla digest`), 텍스트 변환, 형식 검증, 테스트 스텁 생성 등은 유료 토큰을 1토큰도 쓰기 전에 일꾼에게 우선 넘긴다.
  3. **모호함 격리 (Ambiguity Isolation)**: 모호한 지시는 일꾼에게 넘기지 않는다. 과거 `--worker auto`의 60점 자동 분기는 구현 이력이며, 현행 운영 계약은 §20 및 `docs/27`의 80점 입력 완전성 관문과 명시적 원격 승격 승인 범위를 따른다.
  4. **3대 도구 공통 의무 (Universal Obligation)**: Codex, Claude Code, Antigravity 3대 도구 모두가 동일하게 일꾼을 부리며, 일꾼을 부리지 않고 유료 토큰을 낭비하는 행위는 시스템 결함으로 간주한다.
- 임시 권한 위임 및 독자행동:
  - Codex와 Claude Code 둘 다 사용 제한·부재(한도 소진, 정지, 무응답) 상태일 때, Antigravity는 Codex·Claude Code의 총괄 조율·계획·수행 권한을 임시 위임받아 독자행동(Autonomous Action)을 수행한다.
  - Antigravity는 조율 계획(`PLAN.md`), 아키텍처 문서, 훅 및 도구 설정을 독자적으로 갱신하고 프로세스를 마무리하되, 영구 안전 한계(데이터 삭제, 원격 push, 배포, 결제, 권한 변경)는 준수하며 Codex 복귀 시 재검토 목록에 모든 근거를 기록한다.

## 18. 올라마 '유선 전화기' 모델 및 0원 디스크 우편함·상주 감시관 아키텍처

(2026-09-24 사용자 지정 고정 규약)

- **유선 전화기 모델 (Telephone Model)**: 올라마는 상시 대기하다가 지휘자가 다이얼을 걸 때(명령 호출) 즉시 연결되어 연산 결과를 반환하는 비용 0원의 유선 전화기다. 분당 과금이 폭증하는 위성전화(유료 API)를 24시간 켜놓고 폴링하는 상주 감시(cron)는 전면 금지한다.
- **음성사서함 (Voicemail)**: 디스크 기반 우편함(`.coord/mailbox/`)을 단일 비동기 버스로 삼아 지휘자 부재 중 메시지 무손실 보존을 목표로 한다. U23 독립 반례가 해결되기 전까지 100% 무손실은 보증하지 않는다.
- **상주 감시관 (Sentinel)**: 로컬 올라마 프로세스는 24/7 교환원으로서 잠금 고착(60분 초과), 원장 미정리, 에러 1차 트리아지, 60줄 초압축 브리핑 생성을 비용 0원에 전담하며, 차단 결함(`BLOCKED P1`) 또는 사용자 승인 대상 발생 시에만 지휘자의 벨을 울린다(Wake-on-P1 Ringing).
- **세밀한 작업명령서 규약**: 올라마는 생각 없는 전자계산기이므로 구체성 80점 이상의 세밀한 작업명령서(`docs/24`)로만 구동하며, 주관적 추론이나 독자적 설계를 요구할 수 없다.

## 19. Codex 부재 시 대화창 메시지 발송 전면 금지 규약

(2026-09-24 사용자 강력 지정)

- Codex가 사용 제한·부재(`LIMITED` 또는 `ABSENT`) 상태일 때, Codex 대화창 및 메시지 큐(`coord notify` / `codex queue`)로의 메시지 발송은 예외 없이 **전면 거부(HARD REFUSE: `CODEX_ABSENT`)**된다.
- 한도 초과 상태인 Codex 대화창에 메시지가 인입되어 한도 에러 화면을 유발하거나 큐를 오염시키는 일체의 시도를 원천 차단한다.
- 모든 비동기 통신과 상황 공유는 0원 디스크 우편함(`.coord/mailbox/`) 및 브리핑 파일(`.coord/codex_brief.md`)에만 스풀링되며, Codex가 활성 복귀할 때까지 대화창 발송을 전면 중단한다.

## 20. 작업별 토큰예산 예측과 품질 보존

(2026-09-24 사용자 지정: Codex·Claude의 한도 보존, Antigravity 대행 빈도 제한, Ollama 실사용 데이터 축적)

- 운영 정본은 [`docs/27`](27_token-budget-routing-policy.md)이다. 계정의 5시간/주간 잔여율과 작업별 전후 변화로 다음 단계의 소모 범위를 예측하되, 세션 토큰과 계정 잔여율을 동일시하지 않는다. 샘플·상태가 부족하면 `UNKNOWN`, 절감 효과는 직접 대조 전 `UNMEASURED`다.
- Codex는 계획·최종 판정 예산을, Claude는 구현·독립 검토 예산을 예약한다. 예산 부족은 먼저 작은 계약과 Ollama 계산으로 대응한다. Antigravity의 총괄 대행은 Codex와 Claude 둘 다 실제 제한·부재일 때만 발동하며, 복귀한 지휘자가 대행 결론을 재검토한다.
- 세 도구는 같은 작업 ID로 Ollama 호출의 입력·출력 로컬 토큰, 시간, 인수 결과를 남겨 10건마다 성공률·재작업률·원격 승격률을 검토한다. Ollama는 **단순 추론·의지 없는 전자계산기, 전화기**이며 판단·승인·판정권이 없다.
- 작업별 실행 절차는 [Claude](28_claude-budget-manual.md)·[Antigravity](29_antigravity-budget-manual.md)·[Ollama](30_ollama-calculator-manual.md) 매뉴얼에 둔다. U23 전달계층의 무손실·반복 기상 주장은 독립 반례가 해결될 때까지 보증하지 않는다.

## 21. 증거 관문형 RSI와 누적 실사용 기록

- [RSI 운영 정본](31_evidence-gated-rsi-for-uaos.md)은 모델의 무제한 자기변경이 아니라 `관찰 → 가설 → 고정 인수 → 작은 후보 → 대조 → 독립 판정`의 프로세스 개선이다.
- Codex·Claude·Antigravity·Ollama의 호출과 실패를 동일 작업 ID로 [사용량 장부](../.coord/usage/README.md)에 축적한다. Ollama는 수치 추출·분류의 계산기이고, 세 유료 도구도 자기 변경의 유일한 검증자가 될 수 없다.
- 개선 효과는 숨은 반례와 같은 기준선으로 비교하고 품질 저하·P1·3배 비용 회귀면 채택하지 않는다. U27 자동 수집 관문 전에는 장부를 수동 부트스트랩으로 표시한다.
