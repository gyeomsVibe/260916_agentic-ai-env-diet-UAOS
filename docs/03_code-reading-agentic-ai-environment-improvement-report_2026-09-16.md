# 코드를 덜 읽는 시대에, 무엇을 더 잘 알아야 하는가

> 「아직도 코드를 읽나요?」와 “코딩 에이전트에게 프로젝트를 어디까지 맡길 것인가”를 바탕으로 정리한 Codex·Antigravity 환경 및 글로벌 룰 개선 보고서

- 작성일: 2026-09-16
- 대상: 코딩 전문지식이 충분하지 않아도 Agentic AI를 안전하고 주도적으로 활용하려는 사용자
- MIA 결정: `GO — 규칙을 더 많이 추가하기보다 의도·권한·증거·책임 구조를 먼저 개선`
- 현재 프로젝트 연결점: `docs/01_unified-agent-orchestration-design.md`의 단일 계획·단계별 대화창·단일 소유자 원칙

## 1. 먼저 결론

“AI 시대에도 코드를 읽어야 하나?”라는 질문에는 하나의 정답이 없다.

더 중요한 질문은 다음과 같다.

> 이 시스템을 앞으로 누가 고치고 책임질 것인가? 그 사람이 판단에 필요한 의도와 증거를 실제로 가지고 있는가?

코드를 전부 읽는다고 시스템을 이해하는 것은 아니다. 반대로 코드를 전혀 읽지 않아도 명세와 평가 체계가 충분하다면 유용한 결과를 만들 수 있다. 위험한 상태는 어느 한 방식을 택한 것이 아니라, **이해를 잃었는데 그 사실을 모르는 상태**다.

따라서 Codex·Antigravity 환경의 목표는 “AI가 코드를 더 많이 쓰게 하기”가 아니다. 다음 네 가지를 잃지 않으면서 위임 가능한 작업 크기를 키우는 것이다.

1. **의도:** 무엇을 왜 만들며 무엇은 만들지 않는가
2. **권한:** 에이전트가 어디까지 현실을 바꿀 수 있는가
3. **증거:** 요구가 충족됐다고 무엇으로 판정하는가
4. **책임:** 문제가 생겼을 때 누가 설명하고 복구할 수 있는가

## 2. 두 글이 말하는 서로 다른 문제

### 기사 A — 「아직도 코드를 읽나요?」

이 글은 AI 활용자를 단순히 “코드를 쓰는 사람”과 “안 쓰는 사람”으로 나누지 않는다.

- **가속형 개발자:** AI로 구현 속도를 높이지만, 병합 전에 구현을 이해하고 유지보수할 수 있는 상태를 확보한다.
- **바이브코더:** 원하는 동작, 맥락, 평가 기준을 관리하고 구현과 지속적 수정은 AI에 위임한다.

차이는 AI가 생성한 코드의 비율이 아니라 **결과물과 맺는 관계**다. 두 방식 모두 거의 모든 코드를 AI가 생성하게 할 수 있다. 다만 전자는 구현 이해를 보존하고, 후자는 구현을 폐기·재생성 가능한 것으로 본다.

글의 중요한 경고는 다음과 같다.

- 코드보다 오래 남겨야 할 자산은 도메인 모델과 결정의 이유다.
- 테스트 통과는 “명령대로 동작한다”는 뜻이지, 그 명령이 현실 문제에 맞다는 뜻은 아니다.
- 모든 코드를 읽어도 `왜 만료 시간이 6시간인가` 같은 결정 이유는 복원되지 않는다.
- 생성 속도가 검토 속도를 추월하면 인지 부채가 쌓인다.
- 같은 팀에서 서로 다른 위임 방식을 쓴다면 시스템 영역별 유지보수 책임과 경계를 먼저 합의해야 한다.

### 기사 B — “코딩 에이전트에게 프로젝트를 어디까지 맡길 것인가”

두 번째 글은 더 실무적인 사고 사례를 보여준다. 사용자가 자동 모드로 에이전트를 운용하다가 등록된 API 키를 통해 실제 비용이 발생했다.

댓글에서 반복된 대응은 세 가지였다.

- 파괴적 권한과 비용 발생 권한을 기본적으로 막는다.
- 작업 계획을 사람이 검토하고, 건드리면 안 되는 영역은 훅이나 하네스로 차단한다.
- 상당 부분을 위임하더라도 배포·공개 같은 마지막 결정은 사람이 맡는다.

즉, 신뢰의 핵심은 “모델이 얼마나 똑똑한가”가 아니라 **모델이 실수했을 때 영향 반경을 운영 환경이 얼마나 제한하는가**다.

## 3. 두 글을 함께 읽어야 보이는 것

| 보이는 질문 | 실제로 결정해야 하는 것 |
|---|---|
| 코드를 읽을까? | 이 영역은 구현 이해형인가, 명세·평가 위임형인가? |
| AI를 믿을까? | 어떤 행동과 영향까지 허용할 것인가? |
| 테스트가 통과했나? | 테스트가 현실의 성공 조건을 대표하는가? |
| 에이전트가 완료했다고 했나? | 독립적으로 확인할 증거와 복구 경로가 있는가? |
| 컨텍스트를 많이 줬나? | 현재 유효한 정보와 폐기된 정보를 구분했는가? |
| 여러 에이전트를 썼나? | 계획·소유권·쓰기 범위가 하나로 조율되는가? |

여기서 얻는 핵심 전환은 다음과 같다.

> 코드 리뷰 하나로 모든 위험을 막으려 하지 말고, 의도 리뷰·행동 리뷰·결과 리뷰를 분리한다.

- **의도 리뷰:** 만들려는 것이 현실 문제와 맞는가
- **행동 리뷰:** 비용, 외부 쓰기, 개인정보, 삭제, 배포 범위가 허용됐는가
- **결과 리뷰:** 인수 조건과 실제 증거가 맞는가

## 4. 사용자가 모르는 것을 모를 때 생기는 위험

### 4.1 AI가 그럴듯하게 정한 값은 요구사항처럼 굳어진다

예를 들어 AI가 비밀번호 재설정 링크를 6시간 후 만료시키도록 만들었다고 하자. 나중에 코드를 읽어도 6시간이 업무 요구인지, 기존 관례인지, 보안 절충인지, AI의 임의 선택인지 알 수 없다.

이것이 **의도 부채(Intent Debt)**다. 해결책은 모든 코드를 읽는 것이 아니라, 중요한 선택을 다음처럼 분류해 남기는 것이다.

- 사용자 요구
- 의도적인 설계 결정
- 기존 시스템에서 물려받은 관례
- 근거가 아직 없는 임시 선택

### 4.2 테스트는 잘못된 목표도 훌륭하게 통과시킨다

테스트는 작성된 기대값을 확인한다. 사용자가 무엇을 빠뜨렸는지, 실제 사람이 이 흐름을 이해하는지, 사업 규칙이 현실과 맞는지까지 자동으로 보장하지 않는다.

따라서 완료 조건에는 최소 두 층이 필요하다.

- **구현 검증:** 빌드, 테스트, 타입, 보안, 성능
- **현실 검증:** 실제 사용자 행동, 업무 규칙, 비용, 운영 가능성

### 4.3 컨텍스트가 많을수록 오히려 틀릴 수 있다

오래된 문서, 실패한 계획, 과거 대화, 생성 로그를 모두 넣으면 AI가 폐기된 정보를 현재 규칙으로 오해할 수 있다. 컨텍스트는 양이 아니라 지위가 중요하다.

- `canonical`: 현재 따라야 하는 정본
- `reference`: 참고만 가능한 자료
- `superseded`: 폐기된 이전 결정
- `untrusted`: 웹·로그·외부 문서처럼 명령 권한이 없는 증거

### 4.4 자동 모드는 비용과 외부 상태까지 자동으로 바꿀 수 있다

API 키가 있다는 것은 사용할 기술적 능력이 있다는 뜻이지, 지출 허가가 있다는 뜻이 아니다. 같은 원칙이 클라우드 생성, 이메일·댓글 전송, 데이터 변경, 배포에도 적용된다.

**도구 접근 가능성**과 **행동 허가**를 분리해야 한다.

### 4.5 인간 승인이 있어도 인간이 판단할 수 없으면 안전하지 않다

승인 화면에 “계속할까요?”만 표시되면 사용자는 결국 습관적으로 승인한다. 승인 전에는 최소한 다음이 보여야 한다.

- 무엇이 바뀌는가
- 어디까지 영향을 미치는가
- 비용 상한은 얼마인가
- 어떤 증거가 있고 무엇이 아직 불확실한가
- 실패하면 어떻게 되돌리는가

### 4.6 생성 속도가 검증 속도를 추월하면 작업이 아니라 부채가 쌓인다

에이전트가 빠르게 많은 변경을 만들어도 사람이 검토하거나 자동 평가할 수 없다면 “완료된 작업”이 아니라 “검증 대기 재고”가 늘어난다. 현재 프로젝트의 `WIP=1` 원칙은 단순한 속도 제한이 아니라 이 위험을 막는 장치다.

### 4.7 사람의 복구 능력도 사용하지 않으면 사라진다

고위험 시스템에서 최종 책임을 사람이 진다고 적는 것만으로는 부족하다. 장애 시 사람이 실제로 판단하고 복구할 수 있어야 한다. 완전 위임 영역이라면 사람의 수동 코딩 능력 대신 재생성 가능한 명세와 독립 평가 하네스가 그 책임을 대신해야 한다.

## 5. 윤겸스에게 적합한 운영 모델

모든 프로젝트에 한 가지 방식을 강요하지 않고, **영역별 위임 모드**를 먼저 선언한다.

### 모드 A — 이해 보존형

다음 영역에 적합하다.

- 보안, 인증, 권한
- 돈과 결제
- 장기 운영할 핵심 도메인
- 데이터 손실이나 규제 위험이 있는 기능

운영 원칙:

- AI가 코드를 생성해도 중요한 흐름과 결정은 사람이 설명할 수 있어야 한다.
- 핵심 diff, 데이터 흐름, 실패 경로를 검토한다.
- 중요한 상수와 정책 결정에는 근거를 남긴다.

### 모드 B — 명세·평가 위임형

다음 영역에 적합하다.

- 일회성 도구와 프로토타입
- 재생성이 쉬운 UI 실험
- 결과를 독립적으로 평가할 수 있는 변환 작업
- 폐기 비용이 낮은 자동화

운영 원칙:

- 구현을 전부 이해하는 대신 목표·제약·인수 조건을 강하게 만든다.
- 구현은 교체 가능하게 하고 데이터와 명세를 분리한다.
- 코드 리뷰보다 시나리오 테스트와 실제 결과를 중시한다.

### 모드 C — 혼합형

대부분의 실제 프로젝트에 적합하다.

- 핵심 도메인·데이터·권한은 이해 보존형
- UI·어댑터·반복 코드·실험은 명세·평가 위임형
- 두 영역 사이에는 명확한 인터페이스와 별도 검증을 둔다.

현재 윤겸스의 Codex–Antigravity 통합 운영은 **모드 C**가 가장 적합하다.

## 6. 현재 단일계획 설계에 추가해야 할 것

기존 설계의 다음 원칙은 그대로 유지할 가치가 있다.

- 하나의 마스터 계획
- `[U##]` 단계별 전용 대화창
- 단계별 단일 소유자
- `WIP=1`
- 수행자는 `REVIEW`, 조율자가 증거 확인 후 `DONE`

여기에 각 작업 카드마다 아래 다섯 필드를 추가하는 것이 좋다.

```markdown
- Delegation mode: understanding | spec-eval | hybrid
- Intent to preserve: 사람이 계속 이해해야 하는 결정
- Permission tier: R0 | R1 | R2 | R3
- External effects: 비용·네트워크·외부 쓰기·공개·배포
- Recovery owner: 실패 시 판단하고 복구할 주체
```

이 추가가 중요한 이유는 대화창과 소유권만 나눠도 **어떤 이해를 보존해야 하는지**와 **어디까지 행동해도 되는지**는 자동으로 정해지지 않기 때문이다.

## 7. 글로벌 룰 개선 방향

글로벌 룰을 더 길게 만드는 것은 목표가 아니다. 여러 도구에 공통으로 필요한 불변식만 남기고, 프로젝트와 작업별 세부사항은 하위 문서에 둔다.

### 글로벌에 남길 최소 불변식

1. 외부 쓰기, 비용, 배포, 공개, 삭제, 계정·권한 변경은 명시적 승인 없이는 실행하지 않는다.
2. 가정과 관찰된 사실을 구분하며, 가정을 요구사항으로 바꾸지 않는다.
3. 에이전트의 자체 완료 보고는 검증 증거가 아니다.
4. 현재 정본과 오래된·외부·신뢰하지 않는 컨텍스트를 구분한다.
5. 동일한 변경 대상에는 한 명의 활성 소유자만 둔다.
6. 비밀은 읽거나 출력하거나 인계 문서에 기록하지 않는다.

### 프로젝트 규칙으로 둘 것

- Codex가 조율자라는 역할
- `[U##]` 이름 규칙
- 상태 기계와 `WIP=1`
- 프로젝트별 빌드·테스트 명령
- 파일·모듈 소유권과 아키텍처 경계

### 작업 카드로 내릴 것

- 이번 단계의 목표와 비목표
- 수정 허용 범위
- 위임 모드
- 인수 조건
- 비용·외부 영향 상한
- 검증과 롤백 방법

이 구조는 “One mutable policy, one owner” 원칙을 지킨다. 같은 규칙을 글로벌·프로젝트·작업 프롬프트에 세 번 복사하지 않는다.

## 8. 위험 기반 권한과 검토 깊이

| 등급 | 대표 행동 | 기본 처리 | 코드 검토 전략 |
|---|---|---|---|
| R0 | 읽기, 조사, 문서 초안 | 자동 수행 | 결과와 출처 확인 |
| R1 | 가역적인 로컬 코드 수정·테스트 | 범위 내 자동 수행 | 핵심 diff와 테스트 확인 |
| R2 | 유료 API, 외부 write, migration, 실제 데이터 | 사전 승인과 상한 필요 | 영향 경로·비용·롤백 집중 검토 |
| R3 | 배포, 공개 게시, 삭제, 계정·권한·자격증명 변경 | 실행 직전 인간 승인 | 전체 영향과 복구 책임 확인 |

검토 깊이는 코드량이 아니라 **실패 반경 × 되돌리기 난이도 × 독립 검증 가능성**으로 결정한다.

## 9. MIA 대안 검토

| 대안 | 가치 | 실현성 | 지속성 | 위험 | 결정 |
|---|---:|---:|---:|---:|---|
| 모든 생성 코드를 사람이 전부 읽기 | 중간 | 낮음 | 낮음 | 생성 속도에 검토가 압도됨 | No-Go |
| AI에 전부 맡기고 결과만 보기 | 높음 | 높음 | 낮음 | 의도·권한·복구 능력 상실 | No-Go |
| 위험별 검토 + 영역별 위임 모드 | 높음 | 높음 | 높음 | 분류 규율이 필요 | Go |
| 글로벌 룰을 계속 상세화 | 낮음 | 높음 | 낮음 | 충돌·컨텍스트 포화 | No-Go |

### MIA 결정

`GO: 혼합형 운영 + 위험 기반 권한 + 의도·증거 보존`

코드를 읽는 행위를 없애거나 의무화하지 않는다. 대신 프로젝트 구역마다 읽어야 할 이유와 읽지 않아도 되는 조건을 명시한다.

## 10. 가장 작은 실험

다음 실제 작업 세 개에만 먼저 적용한다.

1. **R0 문서 작업:** 구현 이해 없이도 출처와 결과만으로 검증 가능한가
2. **R1 기능 작업:** 핵심 결정만 보존하고 나머지 구현은 AI에 맡길 수 있는가
3. **R2 외부 API 작업:** 비용 상한, 외부 효과, 승인, receipt가 실제 오작동을 막는가

각 작업에서 다음을 측정한다.

- 계획·규칙을 읽는 데 든 시간
- 사용자가 개입한 횟수
- 근거 없는 선택 발견 수
- 검증 실패와 재작업 수
- 비용 또는 외부 부작용
- 문제가 생겼을 때 복구 가능 여부

성공 기준:

- 무승인 외부 효과 0건
- 근거 없는 중요 결정의 정본 승격 0건
- 검증 증거 없는 `DONE` 0건
- 소유권 충돌 0건
- 사용자가 최종 성공 기준을 자신의 말로 설명 가능

## 11. 사용자가 작업 전 확인할 30초 질문

에이전트에게 큰 작업을 맡기기 전에 아래만 확인한다.

1. 이 결과는 버릴 수 있는가, 장기간 유지해야 하는가?
2. 내가 계속 이해해야 하는 핵심 결정은 무엇인가?
3. AI가 돈, 외부 데이터, 공개 상태를 바꿀 수 있는가?
4. 성공 여부를 코드 설명 없이 관찰할 방법이 있는가?
5. 실패했을 때 누가 무엇을 기준으로 복구하는가?

답할 수 없는 항목이 있다면 실행을 막기보다, 해당 항목을 작업 카드의 `Unknown`으로 기록하고 먼저 축소 실험을 한다.

## 12. 사실·해석·미확인 사항

### 확인된 사실

- 「아직도 코드를 읽나요?」는 코드 생성 비율보다 결과물과의 관계, 도메인 이론, 인지·의도 부채, 유지보수 경계를 핵심으로 다룬다.
- GeekNews 33727의 작성자는 자동 모드에서 등록한 API 키를 통해 실제 비용이 발생한 경험을 공유했다.
- 해당 글의 댓글은 파괴적·비용 권한 차단, 계획 검토, 하네스, 최종 배포·공개 결정의 인간 보유를 제안했다.
- 현재 프로젝트 문서는 이미 단일 계획, 단계별 대화창, 단일 소유자, 증거 기반 완료를 채택하고 있다.

### 이 보고서의 해석

- 윤겸스의 환경에는 가속형과 바이브코딩 중 하나를 고르는 것보다, 시스템 영역별로 위임 모드를 선언하는 혼합형이 적합하다.
- 글로벌 룰은 행동 안전의 최소 불변식만 소유하고, 이해 보존과 검증 방식은 프로젝트·작업 카드로 내려야 충돌이 줄어든다.

### 아직 확인되지 않은 것

- 이 규칙이 실제 토큰·시간·비용을 줄이는지는 통제 실험 전에는 `UNMEASURED`다.
- 코드 검토를 줄였을 때 장기 유지보수성이 좋아지는지 나빠지는지는 프로젝트별 장기 관찰이 필요하다.
- 현재 작업 폴더는 Git 저장소가 아니므로 변경 이력, 브랜치 격리, worktree 기반 충돌 방지는 아직 검증되지 않았다.
