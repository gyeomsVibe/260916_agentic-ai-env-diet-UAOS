# 80. 대기가 길어지면 스스로 깨어나기 (U179 조각 A)

상태: 유지 문서(maintained). 코드 `v7_harness/coord/watch.py`(`_stalled_wait`, `STALL_SCAN_S`),
`v7_harness/coord/stall.py`(`scan`), 시험 `tests/test_u179_wait_watchdog.py`.

## 1. 무엇이 문제였나

"30분 넘게 기다리면 다른 도구로 돌린다"(U166, 긴 대기 절차)는 `stall.scan`이 한다. 그런데 이 함수를 자동으로
부르는 곳은 **프롬프트 훅 하나**뿐이었다. 훅은 누군가 대화창에 글을 쓸 때만 돈다. 그래서 세 도구가 모두 가만히
기다리고 있으면 절차가 한 번도 실행되지 않았다(2026-10-10 사용자 보고, 재현 `.work/d4/report.md`).

## 2. 무엇을 바꿨나

각 도구가 이미 켜 두는 우편함 감시(`coord watch`)가 60초마다 `stall.scan`을 직접 부른다.

| 항목 | 내용 | 이유 |
|---|---|---|
| 주기 | 60초(`STALL_SCAN_S`) | 한도 1800초의 3% 안에서 늦고, 2초마다 도는 우편함 확인보다 무거운 일이라 따로 돈다 |
| 깨우는 대상 | 그 대기의 작성자, 기다리는 상대, 넘겨받을 도구 | 관계없는 도구까지 깨우면 대기 하나에 유료 턴 세 번을 쓴다 |
| 한 번만 | 대기 한 건(항목 + 시작 시각)마다 영수증 하나(`claim_wake`) | 감시를 다시 켜도 같은 대기로 두 번 깨우지 않는다 |
| 결과 | `{"reason": "STALLED_WAIT", "item": …, "owner": …}` 한 줄로 감시가 끝난다 | 세션이 깨어나면 프롬프트 훅이 무엇을 할지 보여 준다 |
| 비용 | 모델 호출 없음(토큰 0) | 파일 읽기와 작은 상태 파일 쓰기뿐이다 |

넘겨받을 도구가 없는 대기(모두 한도·부재)는 작성자를 깨운다. 그 세션이 `BLOCKED`를 기록하고 다음 카드로 간다.

## 3. 전제와 남은 틈

- **감시가 켜져 있어야 한다.** `coord watch`가 꺼진 도구는 깨어나지 못한다. 그때는 예전처럼 프롬프트 훅과
  `uaos coord stall`이 남은 경로다.
- 옛 방식(`--policy legacy`) 감시는 이 확인을 하지 않는다.
- 아직 하지 않은 것(다음 조각): 이미 전달된 편지(`DISPATCHED`, `PUBLISHED`)의 대기 기록, 깨우기 직전에 죽은
  감시의 영수증 복구. 설계는 `.work/cards/U179_claude_proposal.md` 7.1, 7.3.

## 4. 확인 방법

- 시험: `python -m unittest tests.test_u179_wait_watchdog` — 프롬프트 훅을 막아 둔 채로 감시만으로 깨어나는지,
  실제 감시 프로세스 8개를 동시에 띄워 깨움이 한 번뿐인지 본다.
- 실제 확인: 감시를 켠 채 30분 넘은 판정 요청 편지가 있으면 감시가 `STALLED_WAIT`로 끝난다.
