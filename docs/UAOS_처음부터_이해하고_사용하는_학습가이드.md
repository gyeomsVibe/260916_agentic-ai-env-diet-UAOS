# UAOS를 처음부터 이해하고 사용하는 학습 가이드

상태: 유지보수 문서 · 2026-09-25 기준 로컬 구현 검증 기록. 처음 보는 사람이 **왜 만들었는지 → 무엇이 고장 났는지 → 어떻게 고쳤는지 → 직접 어떻게 쓰는지** 순서로 읽도록 작성했다. 실행 규칙의 정본은 [통합 계획](../.coord/PLAN.md)과 [설계](01_unified-agent-orchestration-design.md)다.

## 0. 먼저 알아둘 세 가지

1. **UAOS**는 Codex·Claude Code·Antigravity·Ollama가 한 프로젝트를 순서대로 다루게 하는 운영 체계다. 네 도구가 동시에 코드를 쓰게 하는 기능이 아니다.
2. **파일럿(pilot run)**은 실제 프로젝트를 복사한 시험 공간에서 작업자를 실행하는 절차다. 시험을 통과해도 원본은 즉시 바뀌지 않는다. 사람이 읽을 수 있는 변경 차이(diff)와 검사 결과를 확인한 뒤 같은 번들(bundle) ID로 반영한다.
3. **완료(DONE)**는 AI가 “끝났다”고 적었다는 뜻이 아니다. 요구사항, 실제 파일, 독립 검사, 사용량 기록이 맞을 때 계획에서 내리는 판정이다.

처음부터 모든 용어를 외울 필요는 없다. 아래 예시를 따라가면서 뜻을 확인하면 된다.

## 1. 왜 이 시스템을 만들었나

사용자의 원래 문제는 “AI 도구를 많이 쓰는데 사용량이 빨리 닳고, 일을 맡긴 도구의 완료 보고를 어디까지 믿어야 할지 모르겠다”였다. 도구를 더 늘리면 같은 파일을 동시에 고치거나 자기 결과를 스스로 합격시키는 문제가 생긴다. 그래서 한 작업에 **계획 1개, 작성자 1명, 고정된 검사 1세트**를 둔다.

| 도구 | 쉬운 비유 | 실제 책임 | 하지 않는 일 |
|---|---|---|---|
| Codex | 현장 책임자 | 순서·범위·검사·최종 판정 | 작업자 말만 듣고 합격 처리 |
| Claude Code | 부책임자 | 독립 검토, Codex가 실제 부재할 때 대행 | 활동 중인 Codex와 같은 단계를 동시 수정 |
| Antigravity | 원격 전문 작업자 | 모호한 탐색·설계·제한된 구현·독립 반례 | 자기 변경의 유일한 검증자 역할 |
| Ollama | **전자계산기이자 유선 전화기** | 호출할 때만 요약·추출·정확한 치환 등 좁은 계산 | 목표·설계·성공·승인 판단 |

“유선 전화기”는 **필요할 때 호출하고 결과를 받는다**는 운영 비유다. Ollama가 사람처럼 의지를 갖거나 독립 운영자가 된다는 뜻이 아니다. “0원”은 이 PC에서 실행할 때 **유료 API 토큰을 쓰지 않는다**는 뜻이다. 전기·시간·하드웨어 비용까지 0이라는 뜻은 아니다. 실제 절감 효과는 별도로 측정한다.

## 2. 사용자의 제안이 실행 가능한 작업이 되는 법

네 AI 도구의 공동 임무는 가공되지 않은 아이디어를 그대로 사실로 선언하는 일이 아니다. 먼저 질문을 구체화하고, GitHub 구현·공식 문서·논문·Reddit 경험담을 **서로 다른 신뢰도의 근거**로 조사한 뒤, 이 PC에서 실행 가능한 작은 작업과 검사로 바꾼다.

1. **질문 정리**: 사용자 말에서 원하는 결과, 원하지 않는 부작용, 비용·권한 경계를 뽑는다. 사용자가 모를 수 있는 전제(설치 여부, 원본 파일 소유자, 실패 시 복구)를 AI가 먼저 점검한다.
2. **근거 조사**: 공식 설명과 코드·실험을 우선한다. Reddit은 현장 반례를 찾는 참고자료이며 보편적 사실의 증명이 아니다. 조사 날짜와 링크를 남긴다.
3. **작업 계약**: 한 단계의 목표, 허용 파일, 검사 명령, 중단 조건, 작성자와 검증자를 적는다. 작업 전에 안티그래비티/올라마 각각에게 이 계약을 담은 **작업 프로세스 매뉴얼**을 발행하고 전달한다.
4. **시험 실행**: Ollama는 규칙이 정확한 단순 노동에 먼저 쓴다. 설계 판단이 필요하거나 좁힌 로컬 과제가 실패하면 Antigravity를 쓴다. 실행 전에 원본을 백업한다.
5. **독립 검증**: 실제 변경 차이(diff), 고정 인수 테스트(acceptance test), 예상 밖 파일 변경, 비용을 확인한다. 작성자가 자기 변경을 혼자 합격시키지 않는다.
6. **반영·기록**: 통과한 번들만 원본에 반영하고 계획 카드·사용량 장부에 실패까지 기록한다. 검증 없이 “100% 절감” 같은 표현을 쓰지 않는다.

### 따라 해 보는 예시: “AI 사용량을 줄여줘”

| 단계 | 막연한 말에서 확인할 것 | 작업 카드에 쓰는 구체적 결과 |
|---|---|---|
| 질문 | 어느 계정의 어느 사용량 창인가? 품질 저하는 허용되는가? | 계정별 5시간·주간 전후 스냅샷, 같은 작업의 품질 인수 |
| 근거 | 공급자 사용량 화면과 실행 영수증이 있는가? | 수치·시각·작업 ID·원본 경로 기록 |
| 작업 | 로그 정리인가, 코드 변경인가? | 로그 추출은 Ollama, 설계 판단은 지휘자/Antigravity |
| 검사 | “줄었다”를 무엇으로 판단하나? | 같은 기준의 전후 비교; 창이 섞였으면 `UNMEASURED` |
| 보고 | 초보자가 무엇을 알아야 하나? | “3개 통제 과제의 입력 대리지표 −76.7%; 계정 한도 절감 미측정” |

이렇게 하면 도구의 자신감 있는 문장과 실제 증거를 구분할 수 있다. [OpenAI의 평가 안내](https://developers.openai.com/api/docs/guides/evaluation-best-practices)는 목표·데이터·지표를 정하고 반복 평가하라고 설명한다. [에이전트 흐름 평가 안내](https://developers.openai.com/api/docs/guides/agent-evals)는 도구 선택과 인계까지 검사 대상으로 삼는다.

## 3. 실제 수행 과정: 진단 → 수리 → 재검증

### 3-1. 토큰 예산을 어떻게 다뤘나

Codex와 Claude Code의 사용률은 공급자별 한도다. `남은 3%`를 “토큰 몇 개”로 바꾸는 식은 믿을 수 없다. 그래서 [예산 규칙](27_token-budget-routing-policy.md)에 계정별 현재 창, 판정용 예약량, 실패 재작업 여유, 작업자 선택 기준을 따로 적었다. Ollama 사용량은 로컬 계산량으로 측정하고, 유료 계정 한도 변화와 섞지 않는다.

같은 3개 통제 과제(P05·P06·P07)에서 Codex **입력 토큰 대리지표 평균 76.7%**, 출력 **97.0%** 감소가 보고됐다. 이는 그 세 과제의 비교 결과다. 이 숫자만으로 실제 구독 계정 한도가 같은 비율로 절약된다고 말할 수 없다. 현재 계정 절감률은 `UNMEASURED`다. 근거는 [R4 측정 카드](../.coord/tasks/R4-additional-measurements.md)와 [계획](../.coord/PLAN.md)의 R4 행이다.

### 3-2. U23: 우편함과 감시관

**우편함(mailbox)**은 도구가 서로 못 만나는 동안 메시지를 디스크에 남기는 장치다. **감시관(sentinel)**은 잠금과 심각한 오류(P1)를 살피는 로컬 절차다. 처음 “완료” 보고 뒤에도 두 반례가 나왔다.

| 발견한 문제 | 사용자가 겪을 수 있는 일 | 수정과 확인 |
|---|---|---|
| 밑줄이 든 메시지 ID 복구가 손상됨 | 보관 중인 메시지가 잘못된 이름으로 돌아옴 | JSON 본문의 ID로 복구; 숨은 검사 통과 |
| 같은 P1 상태를 반복 감시할 때 경고 중복/충돌 | 같은 문제로 여러 번 깨우거나 감시가 멈춤 | 사건 내용 지문(fingerprint)으로 중복 억제; 숨은 검사 통과 |

Codex는 기존 단위 테스트 밖의 숨은 검사 **3개**를 다시 실행해 모두 종료 코드 0을 확인했다. 이는 문제 유형 세 개라는 뜻이 아니다. 확인된 문제 유형은 위 표의 **두 가지**이며, 세 검사 각각의 파일명·명령과 결과는 [U23 카드](../.coord/tasks/U23-mailbox-foundation.md)와 [복귀 점검 기록](../.coord/runs/codex_return_verification_summary.json)을 따른다. “24시간 안정”은 별도의 장기 운영 실측이 필요한 표현이다.

### 3-3. U27: 사용량 장부가 왜 다시 고쳐졌나

**사용량 장부(ledger)**는 누가 어떤 도구를 얼마나 썼고 어떤 검사 결과가 났는지 한 줄씩 덧붙이는 파일이다. 초기 U27 코드는 겉으로 테스트가 통과했지만 네 가지 문제가 있었다.

1. 잠금(lock)을 10초 동안 못 얻으면 잠금 없이 기록했다. Windows에서 다른 프로세스와 부딪히면 줄이 손상·유실될 수 있었다.
2. 테스트가 스레드(thread) 네 개만 사용했다. 실제 Windows의 서로 다른 프로세스(process)가 동시에 기록하는 상황을 보지 못했다.
3. 자동 기록 형식이 정본 `uaos-usage-v2`와 달랐다. 기록이 쌓여도 같은 기준으로 비교하기 어려웠다.
4. 기록 실패를 조용히 무시했다. 사용자는 장부가 비었는데도 정상이라고 생각할 수 있었다.

수리는 세 번들로 분리했다: [장부 코드](../v7_harness/coord/usage_ledger.py)의 잠금 실패 시 거부(fail-closed)와 v2 검증, [테스트](../tests/test_u27_usage_ledger.py)의 Windows 다중 프로세스 검사, [파일럿](../v7_harness/pilot.py)의 자동 기록·오류 표시. 숨은 검사에서는 **8개 프로세스 × 25건 + 처음 1건 = 201건**이 모두 다른 ID의 올바른 JSON 행이었다. 잠금 시간초과 중 추가 기록은 **0건**이었다. 실제 파일럿 한 번은 장부를 **24행에서 25행**으로 늘렸다. 상세 영수증은 [U27 카드](../.coord/tasks/U27-usage-ledger-automation.md)에 있다.

이 과정에서 Ollama가 `pilot.py` 전체를 짧은 파일로 잘라낸 초안도 나왔다. 컴파일만 통과했으므로 반영하지 않았다. 이후 Antigravity의 제한된 수리를 독립 검사 후 반영했다. 이 반례가 “작업자 성공 보고보다 diff와 실제 동작이 우선”이라는 규칙의 이유다.

### 3-4. RSI: 시스템이 스스로 나아지는 범위

**RSI(반복적 자기 개선, recursive self-improvement)**는 여기서 AI에게 규칙과 권한을 마음대로 바꾸라는 뜻이 아니다. 실행 기록으로 실패 가설을 세우고, 고정된 인수 테스트와 독립 검증을 통과한 작은 변경만 채택하는 절차다. [RSI 정본](31_evidence-gated-rsi-for-uaos.md)은 `관찰 → 가설 → 고정 인수 → 작은 후보 → 대조 → 독립 판정` 순서와 실패 표본 보존을 규정한다.

예를 들어 “로컬 모델이 큰 파일을 자주 망친다”는 관찰이 나오면, 파일 크기·지시 구체성·실패 유형을 같은 작업 ID로 모은다. 그런 다음 **파일 전체 재작성 금지** 같은 작은 개선안 한 개를 시험한다. 성공률과 비용이 함께 좋아지고 기존 인수가 유지될 때만 채택한다. [Self-Refine 논문](https://arxiv.org/abs/2303.17651)의 반복 개선 아이디어를 참고하되, UAOS의 채택 기준은 이 프로젝트의 독립 검사다.

## 4. 직접 쓸 때의 순서

프로젝트 루트는 `260916_agentic-ai-env-diet`다. 먼저 [사용자 빠른 안내](33_uaos-final-user-guide-and-completion-briefing.md)를 연다. 아래는 각 명령의 **뜻을 이해하기 위한 형식 예시**다. `U##_NAME`, 프롬프트 경로, 테스트 이름은 실제 작업 카드의 값으로 바꿔야 한다.

```powershell
# 1. 목표·허용 파일·검사·중단 조건을 해당 작업 카드와 매뉴얼 파일에 먼저 적는다.
# 2. 아래 --prompt-file로 매뉴얼 내용을 작업자에게 실제 전달한다.
# 3. 로컬 작업자라면 Ollama 실행 여부와 모델 설치를 사전 확인한다.
ollama list
# 4. 원본은 아직 바꾸지 않고 시험 공간에서 실행한다.
python -m v7_harness.cli pilot run --task U##_NAME --source . --prompt-file .coord/tasks/해당-작업명령서.md --accept-cmd "python -m unittest tests.test_target" --work-dir .work/pilot_U##_NAME --worker local

# 5. 출력의 bundle_id와 summary_path를 읽고 summary.json의 verdict_hint를 확인한다.
Get-Content -Raw .work/pilot_U##_NAME/runs/U##_NAME/summary.json
# 6. bundle_id를 복사해 실제 변경 diff·인수 로그와 대조한 뒤에만 반영한다.
python -m v7_harness.cli pilot run --task U##_NAME --source . --prompt-file .coord/tasks/해당-작업명령서.md --accept-cmd "python -m unittest tests.test_target" --work-dir .work/pilot_U##_NAME --worker local --approve "BUNDLE_ID_FROM_SUMMARY"
```

**자주 놓치는 점**: `ollama list`가 실패하거나 필요한 모델이 없으면 로컬 실행을 멈추고 원인을 확인한다. `PASS`는 파일럿이 제시한 후보가 정해진 검사에 통과했다는 신호다. `--approve` 전에는 원본 변경이 반영되지 않는다. `bundle_id`는 예시 문자열이 아니라 **방금 실행한 출력·summary.json의 값**을 사용한다. `NO_CHANGES`는 “일을 잘 끝냈다”가 아니다. `SOURCE_DIVERGED`면 실행 중 다른 작성자가 원본을 바꾼 것이므로 원인을 확인하고 새 작업으로 검증한다. `NEEDS_RECONCILIATION`이면 카드의 원장 정리 명령을 먼저 실행한다.

## 5. 결과를 어떻게 믿나

| 확인 질문 | 보아야 할 증거 | 현재 상태 |
|---|---|---|
| 도구가 실제로 파일을 고쳤나? | 원본·후보 diff, 변경 파일 목록, 번들 ID | U27 수리 번들 3개 반영 |
| 잘못된 입력도 견디나? | 밑줄 ID, 반복 P1, Windows 병렬·잠금 실패 반례 | U23 숨은 검사 3/3, U27 숨은 병렬 검사 통과 |
| 기존 기능도 유지되나? | 전체 회귀 테스트(regression test) | 2026-09-25 기준 580개 실행, 1개 건너뜀, 실패 0 |
| 부재 중 대행 변경은 다시 봤나? | Codex 복귀 점검 목록과 직접 실행 | 13/13 통과 |
| 실제 계정 한도가 절약됐나? | 같은 사용량 창의 계정 전후 스냅샷 | `UNMEASURED` |

초기 R1 비교는 B쪽 시험기가 시작 전에 실패했으므로 절감률 근거에서 뺐다. 실패 사실 자체는 남겨야 한다. R2/R4는 별도 통제 비교다. 이전 “Antigravity 유료 토큰 0·100% 절감” 보고도 U27 수리에 원격 토큰이 실제 쓰인 사실과 충돌해 철회했다.

## 7. 지금 남아 있는 불확실성

로컬 구현과 당시의 테스트는 완료됐다. 앞으로 새 작업과 새 버전이 생기면 매번 같은 관문을 적용해야 한다. 장기간 무중단 운영, 실제 공급자 계정 한도 절감률, 원격 배포에서의 동작은 아직 측정되지 않았다. 이 상태를 “모든 환경에서 영구 무결함”으로 읽지 않는다.

문서를 다 읽지 않아도 된다. 첫 작업을 시작할 때는 **무엇을 바꿀지, 어디까지 허용할지, 무엇을 실행해 합격을 확인할지** 세 가지를 카드에 적고, 모르는 전제는 AI에게 먼저 확인시키면 된다.
