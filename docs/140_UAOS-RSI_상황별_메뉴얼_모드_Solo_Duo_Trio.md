## 0. 한 줄 요약 (초보자용)

> **지금 살아 있는(ACTIVE) 도구 수가 곧 모드다.** 1개면 SOLO(혼자 끝내고 실가동), 2개면 DUO(기본 단위: 한 쪽이 만들고 다른 쪽이 판정), 3개면 TRIO(실가동 뒤 정해진 기간 동안 셋이 함께 고치는 베타 테스트). 0개면 HALT(로컬 Ollama 작업만).

확인 명령 (토큰 0, 결정적 계산):

```powershell
python "$HOME/.uaos/uaos.py" coord mode --show --project .
```

출력 예: `{"mode": "DUO", "regime": "DUO_CODEX_CLAUDE", "active": ["codex","claude"], "unknown": [], "fail_closed": false, ...}`

- `fail_closed: true` 이면(상태를 모르는 도구가 있거나 HALT) 종료 코드 1. **모르는 도구(UNKNOWN)는 절대 살아 있는 것으로 세지 않는다.** 그래서 모드는 실제보다 낮게 나올 수는 있어도 높게 나오지는 않는다.
- `budget_mode`는 별개 개념인 토큰 절약 모드(`.coord/mode.json`, 기본 `token-thrift`)다. 혼동 방지를 위해 함께 출력한다.

## 2. 모드 설계

### 2.1 공통 규칙 (모든 모드)

1. **판정자 ≠ 작성자 (`author != judge`)**: 자기 작업을 스스로 승인하지 않는다. 판정자가 없으면 승인하지 않고 "보류된 재검토(deferred re-review)"로 남긴다.
2. **사람 전용 경계(Safety)**: 데이터 삭제, main 원격 push, 배포·공개 게시·스토어 제출, 지출, 계정·자격 증명·권한·시스템 설정 변경은 어느 모드에서도 윤겸스 몫이다. "모든 권한 대행"은 이 목록을 **제외한** 권한이다.
3. **토큰 분배 목표**: Ollama 50% / 도우미(helper) 30% / 핵심(core) 20%. **장부(ledger)로 측정되기 전까지 UNMEASURED(미측정)** 이며 절감 주장 금지.
4. **UNKNOWN은 근거가 아니다**: 상태를 모르면 그 도구는 없는 것으로 계산한다.

### 2.2 모드별 표

| 항목 | SOLO (1도구) | DUO (2도구, 기본) | TRIO (3도구, 베타 테스트) |
|---|---|---|---|
| 진입 조건 | `coord mode` = SOLO (ACTIVE 1개) **또는** 윤겸스가 연 `[긴급]` 독립 창 | ACTIVE 2개 | ACTIVE 3개 **그리고** 실가동된 결과물에 `[자가구현/테스트]` 꼬리표가 붙어 있음 |
| docs/136 regime | `SOLO_CLAUDE` / `SOLO_CODEX` / `SOLO_AGY` | `DUO_CODEX_CLAUDE` / `DUO_CLAUDE_AGY` / `DUO_CODEX_AGY` | `TRIO` |
| 역할 | 한 도구가 설계→구현→테스트→기능 브랜치 커밋·push·PR→런타임 재설치→실가동까지. 같은 도구 안의 서브에이전트·Ollama는 **도우미**일 뿐 판정자가 아니다 | 좌뇌(작성자) + 우뇌(판정자). 작성자는 docs/136 2.3 작성자 순서(claude→antigravity→codex), 판정자는 남은 쪽 | 모니터링 → 문제 수집 → 셋이 분담해 수정·보강 (각 수정은 DUO 짝으로) |
| 관문(gate) | 고정 인수 테스트 + 전체 테스트 통과, 실패는 RSI 영수증(`.coord/usage/`)으로 기록 | 판정자가 직접 돌린 고정 인수 + 독립 판정(PASS/REVISE, ≤5 근거 턴) | 정해진 모니터링 기간 종료 + 열린 문제 0 또는 모두 카드화 |
| 끝(종료) | 실가동 + 보고(사용자·다른 도구) + **보류 재검토 큐 등록** | 판정 PASS + 병합(병합 권한 도구) + 런타임 반영 | 3도구 합의로 `[자가구현/테스트]` 꼬리표 제거 |
| 상향 | 두 번째 도구가 ACTIVE → DUO. 보류 재검토를 그 도구가 **먼저** 처리 | 세 번째 도구 ACTIVE + 실가동 결과물 있음 → TRIO 베타 | — |
| 하향 | 0개 → HALT (로컬 작업만, presence 변화 시 깨움) | 하나가 한도 → SOLO (docs/136 2.5의 1:1 대행 절차) | 하나가 한도 → DUO로 베타 계속, 기간 연장 금지 |
| 토큰 분배 | 핵심 모델은 설계·판정만, 나머지는 Ollama·도우미 (50/30/20, UNMEASURED) | 동일. 작성자·판정자 각각 자기 구독 한도 안 | 모니터링은 결정적 스크립트·Ollama(0토큰), 수정에만 유료 |

### 2.3 모드 사이에 넘어가는 것 (인계물)

| 넘어가는 것 | 위치 | 이유 |
|---|---|---|
| 보류 재검토 목록 (SOLO에서 판정자 없이 실가동한 것) | `.coord/results/<카드>.md` 의 `deferred_review: <도구>` 줄 | 돌아온 도구가 가장 먼저 독립 판정한다 (자기 승인 금지 보완) |
| RSI 실패 영수증 | `.coord/usage/`, `coord log --kind BLOCKED` | 같은 원인 두 번(또는 P1 한 번)이면 수정 카드 |
| 카드 소유·창 | `coord window`/`coord lanes` 기록, 우편함(`coord deliver`) | 창이 바뀌어도 일이 사라지지 않게 |
| `[자가구현/테스트]` 꼬리표 | 결과 파일·PR 본문 | TRIO 베타가 끝나야 제거 |

### 2.4 베타 테스트(TRIO) 기간

- 기간은 카드마다 **실가동 후 정해진 창(window)** 으로 적는다(예: "실가동 후 24시간 또는 다음 3회 실사용"). 무한 모니터링 금지 — AutoGen의 종료 조건처럼 **끝을 먼저 정한다**(RESEARCH F6).
- 기본값은 아직 측정 근거가 없으므로 카드에 숫자와 이유를 적는다(설명 없는 숫자 = 결함).

## 3. 상황별 지시 프롬프트집 (복사·붙여넣기용)

> 사용법: `< >` 자리표시자만 바꿔서 해당 창에 붙여 넣는다. 모든 프롬프트 끝에 공통 경계가 붙어 있다고 본다:
> **[경계] 데이터 삭제·main 원격 push·배포·공개 게시·지출·계정/자격 증명/권한/시스템 설정 변경은 윤겸스 확인. PR 병합은 판정 PASS 후 병합 권한 도구(Antigravity→Codex)만. 그 밖의 승인·판정·다음 카드는 도구끼리 처리.**
>
> 원문 대비 고친 점: ① "모든 승인 대행/모든 권한 위임"은 위 경계를 **제외**한 권한으로 한정 ② "로그·Ollama 기록 순차 제거"는 **dry-run 목록 작성까지만**, 실제 삭제는 사람 몫 ③ "무인·무승인·논스톱"은 "사람 전용 목록 밖에서" 로 한정 ④ 겹치던 프롬프트(B4 해동과 B5 한도 복귀, B6의 도구별 3개 블록)를 하나의 템플릿 + 자리표시자로 합침 ⑤ 사용자에게 다시 일을 넘기는 문구 제거.

### P1. 통합 사용자 창(총괄 디렉터) 선언 — 원문 B1
- 언제: 윤겸스가 새 대화창을 상위 창으로 정할 때. / 모드: 선언 자체는 모드와 무관(라우팅만), 이후 작업 모드는 `coord mode --show` 결과(SOLO/DUO/TRIO)를 그대로 따른다.
```text
[UAOS-DIRECTOR] 이 창 = 통합 사용자 창(총괄 디렉터). 모든 도구·카드 창은 여기로 보고한다.
1) 출석 체크: coord presence + coord mode --show 결과를 한 줄로.
2) 전수 파악(/DEEPDIVE /REDTEAM): 진행 중 카드·창 목록, 중복 미구현 창은 통폐합 후보로 표시.
3) 오늘의 도우미 모델 확인(필수) → 토큰 사용 예측 → 마스터/세부 스케줄([긴급] 포함) 작성.
4) Ollama·도우미 사용은 매번 기록, 주기 점검해 RSI 개선 후보로.
[경계] 위 공통 경계.
```

### P2. [긴급] 독립 창 — 원문 B2 (SOLO)
- 언제: 윤겸스가 `[긴급]` 창을 열었을 때. / 모드: **SOLO** (그 창 단독 완주).
```text
[UAOS-URGENT card=<카드ID>] 이 창은 [긴급] 독립 창이다. 모드 SOLO.
1) 기존 미구현 스케줄 중 <카드ID>와 겹치는 것을 이 창으로 이관(중복은 정리 목록으로).
2) 설계 → 구현 → 전체 테스트 → 기능 브랜치 커밋·push·PR → 런타임 재설치 → 실가동.
3) 실패·수정은 RSI 영수증으로 기록, 판정자 없던 부분은 deferred_review 로 남긴다.
4) 결과를 디렉터 창과 다른 도구에 RESULT 한 줄로 보고.
[경계] 위 공통 경계 (main 병합 승인은 병합 권한 도구 또는 윤겸스).
```

### P3. 다른 도구의 사용자 창 → 긴급 창 지원 (태스크포스) — 원문 B2 후반
- 언제: [긴급] 창이 열렸고 이 도구가 ACTIVE일 때. / 모드: DUO (긴급 창의 작성자 + 이 도구의 판정자).
```text
[UAOS-TF card=<카드ID>] [긴급] 창 <카드ID>를 지원한다. 모드 DUO, 나는 판정자/보조.
1) 잠든 카드 창을 깨우고 속도를 맞춘다. 밀리면 대기 대신 전담 독립 카드 창을 새로 연다.
2) 긴급 창 결과를 독립 판정(≤5 근거 턴), REVISE면 근거와 함께 회신.
[경계] 위 공통 경계.
```

### P4. 카드 통제권 이관 (카드별 병렬 세션) — 원문 B3
- 언제: 한 도구가 끝내지 못한 카드가 남았거나 새 디렉터 창이 생겼을 때. / 모드: 이관 뒤 받는 창의 `coord mode` 결과(보통 DUO).
```text
[UAOS-HANDOVER from=<도구> to=<디렉터 창 또는 예비 디렉터 창>]
1) 먼저 중복 미구현 작업 창을 전수 조사해 통폐합 후보 목록을 디렉터 창에 보고.
2) 내가 끝내지 못한 카드 <카드ID 목록>의 통제권을 새 사용자 창으로 넘기고, 해당 카드 창에 알린다.
3) Antigravity 디렉터 창에도 같은 목록을 보고한다.
[경계] 위 공통 경계. 창·폴더 삭제 없음(통폐합 = 소유 이전).
```

### P5. 해동 / 한도 복귀 (통합 템플릿) — 원문 B4 + B5
- 언제: 한도 해제, 대기 해제, "사용 한도가 초기화됐다" 메시지. / 모드: 복귀 후 `coord mode`가 판정.
```text
[UAOS-THAW gen=<세대> card=<카드ID> relay=<릴레이ID> tool=<도구>] 한도/대기 해제.
1) coord presence --tool <도구> --state ACTIVE, coord mode --show 로 현재 모드 확인.
2) coord inbox 의 미확인 릴레이 <릴레이ID>와 체크포인트를 먼저 마무리.
3) 보류 재검토(deferred_review: <도구>)가 있으면 그것부터 독립 판정.
4) 모든 카드 창 세션을 동기화하고, 멈춘 지점부터 재개하도록 각 창에 알린 뒤 다음 READY 카드로 진행.
[경계] 위 공통 경계.
```

### P6. 도구 X 한도 정지 (얼음땡 로직) — 원문 B6 (도구별 3블록을 1개로)
- 언제: 한 도구가 5시간·주간 한도로 멈췄을 때. / 모드: 남은 도구 수로 DUO 또는 SOLO. 절차 정본은 docs/136 2.5.
```text
[UAOS-FREEZE tool=<한도 걸린 도구> until=<리셋 시각>]
1) 남은 도구들이 합의해 <도구>의 역할을 나눠 맡는다(사람 전용 목록 제외 권한 대행).
   단, Codex 전용 핵심 키포인트는 Codex 복귀까지 대기열(QUEUE_FOR_CODEX).
2) <도구>가 진행하던 작업 현황을 전수 파악(/DEEPDIVE /REDTEAM)해 인계 파일로 남긴다.
3) 모든 카드 창에 "<도구> 정지, 대행자=<도구들>"을 알려 혼선·병목·무한 대기를 막는다.
4) 한도 걸린 도구는 정지 직전 자기 카드 창들에 스스로 이 사실을 알린다.
5) 얼음땡: <도구>가 돌아오면 P5로 깨우고, 그동안의 현황을 설명한 뒤 대행 결과를 재검토하게 한다.
[경계] 위 공통 경계.
```

### P7. 복귀한 도구의 완성 점검 — 원문 B7
- 언제: 한도에서 돌아온 도구의 첫 턴(P5 직후). / 모드: SOLO→DUO 상향(복귀 도구 = 판정자).
```text
[UAOS-RETURN tool=<복귀 도구>] 멈춘 사이 다른 도구가 진행한 결과를 비판적으로(/CRITIC) 점검한다.
1) 대행 결과·보류 재검토를 독립 판정.
```

## 4. 실행 체크리스트 (모드별 5줄)

- **SOLO**: `coord mode --show` → 카드 결과 파일에 `deferred_review: <돌아올 도구>` → 전체 테스트 → 기능 브랜치 PR → 실가동 보고.
- **DUO**: 작성자/판정자 지정 → 판정자가 고정 인수 직접 실행 → PASS 후 병합 권한 도구가 병합 → 런타임 재설치.
- **TRIO**: 모니터링 기간·종료 조건 기록 → 문제 수집(0토큰) → 수정은 DUO 짝으로 → 꼬리표 제거 합의.
- **HALT**: 로컬 Ollama·결정적 작업만, presence 변화 감시(0토큰), 유료 폴링 금지.
- **모든 모드**: 사람 전용 목록은 윤겸스 확인, 절감 수치는 장부 측정 전 UNMEASURED.

## 5. 알려진 한계 (Unknowns)

- `coord mode`는 presence만 본다. presence 심장박동(heartbeat)은 만료 시각이 지나면 스스로 UNKNOWN이 되므로 오래된 ACTIVE는 세지 않는다. 다만 docs/136 `detect_regime`(`nowait.peer_alive`)은 더 짧은 신호 신선도 기준을 써서, 드물게 `coord mode`가 한 단계 높게 나올 수 있다 — 디스패치는 regime/participation 쪽이 기준이다. 실제 유료 실행 가능 여부(쿼터 승인)는 `coord participation`(S5)이 판정한다 — 두 출력이 다르면 participation 쪽이 디스패치 기준이다.
- 50/30/20 분배와 "DUO가 TRIO보다 싸다"는 가설은 **UNMEASURED**. 카드 장부 10건 이상 비교 전까지 수치 주장 금지 (RESEARCH H1–H3).
- TRIO 베타 기간 기본값은 측정 근거가 없어 카드별로 정한다.
