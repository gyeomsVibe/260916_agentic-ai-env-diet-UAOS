## Findings

### P1
- **P1-A Forged Codex rollouts written into Codex's own session store.** `process_lanes._ensure_codex_lane_rollout` writes a `session_meta` stub (`source: uaos-lane-window`) under `_codex_sessions()`, which is the real `~/.codex/sessions` by default. These stubs exist only so the U134-R F1 verifier `_verify_thread` passes for a thread Codex never created. This games an evaluator by forging its input, and it writes into another tool's state outside the project.
  - Evidence: the real `~/.codex/sessions/2026/11/01` already holds **254** such stubs from test runs. One was created by another session's run under a `.work/` path. One sandboxed full-suite run created 56 stubs, so every normal suite run pollutes the real store.
  - Whether `codex exec resume <stub-id>` works is UNKNOWN (it was not tried, because it is a paid call).
  - Required: stop writing into the Codex store. A lane gets a Codex thread only when a real thread is created (`_open_codex`) and its id read back. Otherwise the lane has no Codex window and its letters are queued. Test runs must isolate `UAOS_CODEX_SESSIONS`. Do not delete the 254 existing stubs: they are user data outside the repo and need 윤겸스's approval to remove.
- **P1-B Stubs hijack bootstrap routing, and unverified lane ids leak to user or other threads.** `_newest_verified_thread` now picks the newest forged stub as the bootstrap target for ordinary Codex letters (probe 9). If a resume fails, the U134 retry uses `_newest_verified_thread`, which can land on another stub or the user's window. At head 7607e68, a fabricated lane id fell straight back to the designated user desk (probe 7). The same pattern remains elsewhere:
  - Antigravity lane windows get deterministic fabricated conversation ids whenever no prompt is given (`open_or_reuse_lane_window`, `audit_and_clear_nonstop_obstacles`, dispatch).
  - `open_or_reuse_card_parallel_windows` records fabricated card window ids in `.coord/windows/<card>.json` for all 3 tools. `window_for`, `session_busy` and card delivery then use them.
  - Required: never record an id as a window without a real session readback. Fail closed (`NO_WINDOW`, then queue) instead of routing to a fallback thread. Add a discriminating test that a lane or card letter can never reach the user desk or newest-thread fallback.

### P2
- **P2-A UNKNOWN presence is treated as ground for acting.** `select_active_tool_for_lane` falls through to `LANE_NON_LIMITED`, which picks a tool whose state is UNKNOWN, and then `FALLBACK_QUEUE`. The dispatch counts `QUEUED_*` as `ok`. The global rule says UNKNOWN is no ground for acting and routes fail closed.
- **P2-B Topmost user-window claim fails open.**
  - `is_child_card_session` returns False for a thread it cannot find, so any unknown thread passed by `--session-id` (CLI default `--actor antigravity`) is claimed as the default user window.
  - With `claude_sessions_root=None` (the CLI path), the `titleSource == "tool"` check is skipped. `uw.claim` and `_entry_change` then register the session before `rename_claude_desktop_session_title` refuses with `CHILD_TOOL_SESSION`, and the result is still `ok: True`.
- **P2-C Claude Desktop's own store is rewritten directly.** `rename_claude_desktop_session_title` replaces Claude Desktop's `local_*.json` while the app may be running: there is no app lock and the app can overwrite it. The `backup_dir` is optional. The rule asks for native rename plus exact-session readback, not editing another app's store.
- **P2-D Cross-project scan.** `sync_claude_desktop_card_sessions` scans `~/.claude/projects/**/*.jsonl` across all projects. It binds child sessions from other projects into this project's `.coord/windows`, and renames other projects' parent session titles. It reads whole transcripts with `read_text`. It also rewrites `rec_path` with plain `write_text`, outside the windows-record lock (not atomic, races `record_window`).
- **P2-E Stacked PR overlaps open PR #259 (U292).** This PR carries the U292 commit `6868699` plus `process_lanes.py`, while #259 (`agy/u292-card-lane-parallel-window-os`) is still OPEN. Merging either PR leaves the other conflicting or duplicating. One of them must be closed or rebased onto the other before merge.
